# 发布面统一重构方案：yield 链 → `sessionContext.publishStream` 直发

> 状态:已实施完成
> 日期:2026-08-29
> 范围:后端(backend-ts)。事件契约/信封/前端零改动。

## 一、问题

迁移前引擎是 async generator:run() 逐层 `yield` 事件,chat-runner for-await 消费并发布。
深层模块(压缩钩子、工具审批)要发事件必须"冒泡"到 run() 顶部,长出了两条旁路:

1. 钩子 `emitStream` 回调 → streamBuffer 缓冲 → 引擎循环内再 yield(hooks.contract 的 EmitStream 契约)
2. 审批 EventBus relay(approval.requested → @OnEvent → streamManager.publish)

两条旁路即 yield 模型对深层不友好的症状。

## 二、DSH 对照(正本)

DSH agent-loop **零 yield**:事件传输不经过生成器。任何深度直接 `session.append()`
(core/agent-loop 11+2 处;工具执行内的审批服务同样直发 `approval/asked`),
append 提交点同步 post-commit 扇出给观察者,host 经 `ctx.on('session/event')` 单点接住。
核心设计:**会话对象本身就是发布面**——谁持有 session,谁就能发事件。

## 三、目标架构

```
深层模块(引擎循环/压缩钩子/审批服务/未来工具)
  └─ sessionContext.publishStream(chunk)     ← 唯一发布面(ISessionContext 方法)
       ├─ prevSeq 组装(读 messageStore.getLastProcessedSeq,"先入库后发事件"契约)
       └─ SessionStreamManager.publish(sessionId, event)
            ├─ eventBuffer 缓存(SSE 重连补发源)
            ├─ 进程内订阅者扇出(bot 回复/子 Agent 捕获)
            └─ relay → SessionEventsService.pushStreamToUser(该用户全部 SSE 客户端)
```

- run() 改 `async run(): Promise<{ finishReason }>`;chat-runner 只 await 完成并收尾
  (stopStream/状态事件/队列消费),不再消费事件——supervisor 职责。
- `streamWithRetry`(LLM 传输层)保留生成器:增量喂 assembler 需要真流,非 SSE 事件通道。
- RequestContext(ALS)包普通 async 闭包,整个 Promise 链都在上下文内(比生成器懒执行更严格)。

## 四、旁路退役

| 旁路 | 处置 |
|---|---|
| 钩子 EmitStream 契约(PreStepPayload/RequestErrorPayload/BeforeCompactionPayload.emitStream) | 删除;压缩协调器经 `sessionContext.publishStream` 直发 compression_start/error/compaction_summary;memory-sync 核实不使用该字段(纯管道) |
| 审批 EventBus relay(APPROVAL_REQUESTED_EVENT + HOOKS.APPROVAL_REQUESTED + @OnEvent) | 删除;EscalationSession 接口加 publishStream(ISessionContext 天然满足),审批帧直发——对齐 DSH 审批应答器 broadcast |
