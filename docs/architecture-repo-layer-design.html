VERDICT

迁移期合理（教科书策略），长期不合理（五处真实错配）；从零设计不设这一层——每个域的 FileStore 直接充当持久化 API。Repo 模式本身不是数据库专属，但它的接口形状（分页、{items,total}、JOIN 水合、CRUD）全部来自 SQL 世界，套在文件存储上是形状错配。它是迁移的脚手架，不是建筑的承重墙——完成使命后应随主库一起退场（已在既定计划内）。

01

"DB 写法"的精确画像

WHAT THE SHELL LOOKS LIKE

现行链路是 Service → Repository（DB 形状接口）→ FileStore（文件实现）。Repository 模式在定义上是"持久化无关"的抽象（PoEAA），但实践中它的方法形状几乎全部从 ORM/SQL 世界继承。这个项目的兼容层带着五个真实痕迹：

症状代码证据来源范式
OFFSET 分页：findAll(skip, limit) → {items, total}character.repository.ts：listCharacters() 全量读后 .slice() 内存切SQL OFFSET/LIMIT + COUNT(*)
JOIN 水合：hydrate() 补 relationsession.repository.ts 补 session.character，注释明言"保持原 Prisma include 形状，调用方零改动"SQL include / JOIN
CRUD 动词：create / update(id, patch) / delete全部 6 个 Repo 的接口面关系表："一行"语义

所以这个直觉有坚实的依据：文件实现只是被塞进了为数据库设计的接口里。"把 repo 换成文件操作"描述的正是这种换芯不换壳的状态。

02

为什么迁移期这样做是对的

SEAM FIRST, SWAP LATER

迁移重构的第一目标不是架构美，是行为等价可验证。保持 Repo 形状换芯，买到三样东西：

收益机制在本项目中的体现
现成的回归网18 个调用方零改动 → 原有测试、HTTP 契约、前端行为全部成为新旧实现的对比基准存储切换的语义变化被限制在 Repo 内部；diff 可 review、出错可二分
介质感知唯一收口"权威来源在哪"只在一个层有答案审计结论能干净到"运行期零 Prisma"——收口让 DB 快照与文件并存期不失控
真实可用的逃生通道表冻结不删 + 接口形状不变上线出大问题时"接回 DB"是把 Store 换回去的事，不是重写

这是标准的 seam-first 重构策略，选择本身没有问题——问题只在于"择机清理"是否真的发生。兼容层的危险从来不是它的存在，而是它悄悄从脚手架变成永久结构。

03

为什么长期留它是错的：五处错配

WHERE THE SHAPE FIGHTS THE MEDIUM
01分页形状隐藏真实成本

SQL 里 OFFSET 是索引扫描、O(page)；文件实现里每次 findAll 都是全量 list 再内存切，O(N)。接口形状让调用方以为翻页便宜。现成案例：侧边栏渐进扫描每轮 limit=25 循环拉，233 个会话下每轮都是全量重排——量级再上一个数量级，这个形状开始疼。

02total 是 COUNT 的遗迹

{items, total} 的唯一消费者是前端算"有没有下一页"。文件范式用游标语义（hasMore + nextCursor）就能以 O(page) 替代 O(N) 的精确计数。

03hydrate 是 JOIN 的遗迹

文件范式下没有"关系"，只有字符串 id。解析时机应归消费者（按需、懒解析），而不是 Repo 每次列表都统一水合——每次 findAll 全量 hydrate 是把 N 次缓存查询做在调用方不需要的时机。

04CRUD 掩蔽领域操作

FileStore 真正贴合文件的 API 是领域动词：writeMetaDirect / rewriteRelativePathPrefix / seedBundledDefaults / childrenOf。Repo 把它们压回 update(id, patch) 再给 Service 用——Service → Repo（压扁）→ Store（还原）绕一圈，还丢了写入语义的精确性（改 title 与 touch 排序键的原子性边界本不相同）。

// 实际调用链： sessionService.update(id, {title}) → sessionRepo.update(id, patch) // CRUD 形状 → sessionStore.writeMetaDirect(meta) // 领域形状（内部再还原出精确写语义）
05双层零增量价值

FileStore 已有缓存、原子写（tmp+rename）、排序键；Repo 是无状态翻译层，唯一功能是"形状兼容 DB 时代调用方"——这件事只该存在到迁移结束。

不设 Repo 的三条理由

其一，可替换性是伪需求。Repo 抽象的价值在于换后端，而你刚做完 SQL→文件的一次性替换，产品语义（目录名即 id、删目录即删会话）已经长进文件布局——换回 SQL 的概率趋近于零，为不存在的需求养一层是纯开销。

其二，领域动词无法泛化。rekey、补种、改路径前缀、childrenOf——这些方法没有"通用接口"可抽象，强行泛化只能得到又一层 CRUD。

其三，Store 本身就是正确形态的 Repository。按聚合根（=目录）组织、领域动词命名、持有缓存与原子写——它已经履行了持久化边界的全部职责，中间再夹一层只有形状税。

与介质无关、依然要守的原则

持久化细节不上浮Service 不知道 meta.json 的存在——这条现有 FileStore 已满足。
排序过滤分页在内存做个人工具量级 <1 万条/域，全量内存排序是对的；别模仿 DB 做查询下推。
写路径全原子 + 单写者tmp+rename 与 mutex 是文件范式的"事务"，缺了它们才有真正的数据丢失风险。
id 语义在 Store 层强制不可改名（改名断引用）与路径安全校验（assertValidId）不是调用方义务。
DESIGN INSIGHT · 布局即语义

文件范式特有的优势：DB 时代"一行会话"对用户不可见，文件时代"一个会话 = 一个目录 = meta + JSONL + workflows"是用户可感知、可利用的领域事实——备份、迁移、排障都是整目录操作。所以从零设计时持久化边界应该故意更薄：允许一部分"实现细节"上升为领域概念（目录名即 id、删库 = rm -rf、改名 = 一条 UPDATE）。这种语义丰富度是 DB 抽象给不了的，也正是硬套 Repo 会把它压扁的原因。
