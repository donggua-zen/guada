01

迁移后的分层现状

WHERE THINGS LIVE NOW

这次重构把 8 个数据域从 SQLite 主库搬进了文件系统（会话 meta.json + JSONL 事件流、角色 AGENT.md、供应商 yaml、机器人 yaml、知识库每库一个 kb.db、MCP yaml、账户 account.json、工作流随会话目录落盘）。调度器 tasks.json 从未走过 DB。启动期由一个显式编排器串行执行各域的一次性导出，各域独立 marker、失败不阻塞、幂等可重跑——这是迁移期最重要的正确性机制。

MigrationBootstrapService显式编排 · 唯一 OnModuleInit
connect → DB migration → 角色 rekey → 供应商 rekey → 账户 → 元信息导出 → KB → 会话消息 JSONL → store 预热。顺序写死在代码里，不依赖 Nest 初始化顺序——历史上三个 bug 都源于此，注释里已明令"不能靠模块初始化顺序碰运气"。
MetadataBootstrapGate启动门控 · 按域放行
一次性导出完成前，各 FileStore 的 initialize() 阻塞在 gate.wait(domain)——防止导出未完成时读到空目录把数据"变没"。已接入：session / bot / account / kb-database / mcp 五个 store。
FileStore 层内存缓存 + 原子写 + chokidar
唯一漏网：CharacterFileStore 没有接 gate（无 gate.wait），靠 CharactersModule 排在 DatabaseModule 之后这一"恰好成立"的模块顺序保证正确。KB meta 走独立的"设置注入后两阶段初始化"，有注释说明，属有意设计。工作流文件按会话懒读、调度器从未是 DB，均无门控需求。
Repository 兼容层common/database/ 下 6 个类
SessionRepository、CharacterRepository、KnowledgeBaseRepository、SessionGroupRepository、KBFileRepository、KBChunkRepository——名字是 DB 时代的，实现已全部委托给文件存储，保留原 Prisma 方法签名让 18 个运行时调用方零改动。功能正确，但位置与命名持续制造"还在走 DB"的误读。
冻结主库ai_chat.db · 17 张表
运行期零访问。唯一能触到它的代码：4 个 bootstrap 服务 + src/scripts/* + MigrationRunner（审计结论与本次扫描一致）。预计两个版本后随脚手架整体移除，上线前正式删除。

运行期隔离已经成立：全代码库直接注入 PrismaService 的运行时模块为 0；import @prisma/client 的只有 prisma.service.ts 与 3 个独立脚本（fix-bot-instances / migrate-messages / seed）。

03

三个重点问题的展开

DEEP DIVE
P0-1

角色链路缺启动门控——唯一漏网的元信息域

迁移体系的原则写在 MigrationBootstrapService 的注释里："顺序是正确性的一部分，不能靠 Nest 模块初始化顺序碰运气"。session、bot、account、kb、mcp 五个域都照此办理（gate.wait + 编排器显式预热），唯独 CharacterFileStore 的 initialize() 没有等任何域。当前它不出事，仅仅因为 DatabaseModule 是 app.module 的第一个 import、CharacterSeedService.onModuleInit 恰好排在 MigrationBootstrapService 完成之后——这正是当年三个顺序 bug 的同款结构。
common/database/bootstrap/migration-bootstrap.service.ts → await this.sessionStore.initialize(); // 有 gate.wait(META_DOMAIN_SESSIONS) → await this.botStore.initialize(); // 有 → await this.mcpStore.initialize(); // 有 // ✗ 没有 characterStore.initialize() —— 它藏在 CharacterSeedService.onModuleInit 里 modules/characters/character-file.store.ts → initialize(): Promise<void> { this.ready ??= this.doInitialize(); } // 无 gate.wait
建议给角色域补一个 META_DOMAIN_AGENTS：CharacterFileStore.initialize() 里 await gate.wait，编排器在 character rekey 完成后 complete + 主动预热。半天工作量，把这最后一个"碰运气"从体系里清掉。
P1-3

KB 持久层在标准 jest 环境整体不可测

109 个测试套件里 104 个绿，5 个失败全集中在 KB（kb-search / kb-chunk / kb-database / kb-file / kb-migration），74 个用例的死因是同一个：better-sqlite3 的原生绑定是按 Electron ABI（NODE_MODULE_VERSION 141）重编译的，系统 Node v22（127）加载直接抛错。也就是说项目最核心的新持久层 kb.db，在当前开发机的标准测试流程里一次都没真正跑过——golden baseline 回归（BM25 分词、FTS 同源等关键防线）只存在于代码里，不存在于验证里。
FAIL test/knowledge-base/kb-search.service.spec.ts FAIL test/knowledge-base/kb-chunk.repository.spec.ts FAIL test/knowledge-base/kb-database.service.spec.ts FAIL test/knowledge-base/kb-file.repository.spec.ts FAIL test/knowledge-base/kb-migration.spec.ts The module '.../better_sqlite3.node' was compiled against a different Node.js version using NODE_MODULE_VERSION 141. This version of Node.js requires 127.
建议双轨方案择一：① jest 专用一份 node-ABI 的 better-sqlite3（pnpm 装到独立目录 + jest moduleNameMapper 指过去），Electron 打包链路不动；② CI 里用 Electron 自带的 node 跑测试。方案①更稳，约半天。
P1-4

兼容层假名——"还是 DB 写法"的直觉来源

用户直觉"很多模块可能还是 DB 写法"，实际扫描结果是：运行期已经没有任何直接 DB 访问。产生这个直觉的根源是命名——6 个类叫 Repository、住在 common/database/、由 database.module 提供，而实现早已全部委托给文件存储。这类"名实分离"是迁移期的合理过渡（保签名、零改动调用方），但收尾期应该开始把名字还回去，否则每个新读者都要重新踩一遍"这到底走不走 DB"的确认成本。
common/database/character.repository.ts → 实际委托 CharacterFileStore common/database/session.repository.ts → 实际委托 SessionFileStore + meta.json common/database/session-group.repository.ts → 实际委托 sessions/_groups.json common/database/knowledge-base.repository.ts → 实际委托 KbMetaStore（kb.json） common/database/kb-file.repository.ts → 实际委托每库 kb.db 的 item 表 common/database/kb-chunk.repository.ts → 实际委托每库 kb.db 的 chunk 表
建议不必一次性大搬迁（会搅浑正在收尾的 diff）。低成本的中间态：每个类头部加一行权威来源声明（"权威来源 = xxx 文件，本类仅保 Prisma 签名"）——部分类已有此类注释，补齐其余；主库移除时再把目录整体改名/下沉到各域模块。

收尾路线建议

5 STEPS · IN DEPENDENCY ORDER
STEP 1
落盘当前工作区先于一切代码改动
把 82+32 个文件按主题拆成可回滚的 commit：附件管线重写（files + attachment utils + 前端 media-type）/ MCP 工具名与门控 / 插件测试 / 设计文档入库 / guada-agent 子模块指针单独一笔。没有这一步，后面任何改动的验证都建立在一团无法二分的 diff 上。
STEP 2
修复测试 ABI 双轨半天
给 jest 一份 node-ABI 的 better-sqlite3（独立安装 + moduleNameMapper），让 KB 五个套件恢复绿色。收尾期的每次改动都需要 KB 回归防线真的在线。
STEP 3
角色域补启动门控半天
META_DOMAIN_AGENTS + gate.wait + 编排器预热，把最后一个"靠模块顺序碰运气"的元信息域纳入既有体系；顺带补齐各兼容层类的权威来源声明注释。
STEP 4
仓库与文档卫生1–2 小时
根目录修复脚本归档到 scripts/archive/（或直接 trash）、.guada_db_repair_backup*.json 明确处置、docs/design 四份范式文档 + technical-debt.md 入库、.gitignore 补 jest 日志与构建残渣。
STEP 5
主库移除清单一并执行按既定节奏：两个版本后
bootstrap 脚手架 + PrismaService + MigrationRunner + 6 个兼容层类整体下沉/删除、全新安装不再生成 ai_chat.db、db:* 脚本清理、跑 scripts/verify-migration.cjs 做逐域断言。此项已在 docs/design/metadata-file-format.md 有 runbook，届时照单执行即可。
