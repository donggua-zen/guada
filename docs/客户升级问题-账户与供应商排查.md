# 客户升级问题排查：账户密码「变默认」与供应商「丢失」

> **历史文档（2026-10）**：Prisma 主库与 DB→文件迁移脚手架已移除。
> 本文排查的启动门控/导出缺陷已随迁移代码一起退役。

> 场景：客户从旧版本升级到本次发版后反馈两个问题
> 1）密码变成了默认值，但用户名还是修改后的（客户也不确定是否记错）
> 2）已经添加的供应商丢失了
>
> **状态（2026-10-14 更新）**：
> - 症状 2 **已定性并修复**——不是数据丢失，是首启索引预热早于迁移导出（客户自测的"新增一个供应商就全部出现"即此症状的指纹），见 §2。已升级客户**重启一次即恢复**。
> - 症状 1 仍为**待取证**：代码里有能产生它的路径（§1.1 C 分支），但需要客户机的 `account.json` 与日志判定；上一版把两个症状当作同一根因的推断已作废（§1.2 已更新）。
>
> 开发者本机无故障现场，本文档为**代码路径分析 + 客户机取证方法 + 立即补救 + 修复状态**。
> 配套只读诊断脚本：[`scripts/diagnose-upgrade-state.cjs`](../scripts/diagnose-upgrade-state.cjs)

---

## 0. 先澄清两件事（避免误判）

1. **代码里没有"默认密码"这个概念。** 账户只有一个判据：`account.json.passwordHash` 有值＝需要登录，为空＝**免登录**（`account-file.store.ts:20-30`）。所以"密码变成默认值"在实现上只能是两种含义之一：
   - ① 从「需要登录」变成「免登录」（密码为空）——对应文件里 `passwordHash: null`；
   - ② 客户用旧密码登不进去（此时密码并没被改，而是根本没导入成功）。
2. **"用户名还是修改后的"不能证明导入成功。** 界面侧栏显示的是 `authStore.user`（`GlobalSidebar.vue:164-166`），而它**在 store 创建时从 localStorage/sessionStorage 恢复**（`stores/auth.ts:17-31`），不会在启动时向后端刷新。也就是说：即使 account.json 被写成了默认账户（username=`guada`），界面**仍然显示客户记忆中的旧用户名**。因此"用户名保留 + 密码没了"是**完全自洽**的一种可能。

## 1. 症状 1：密码没了

### 1.1 唯一会「写掉密码」的代码路径

`account-bootstrap.service.ts` 的引导逻辑（`bootstrap()` :56-75）：

| 分支 | 触发条件 | 结果 |
|---|---|---|
| A 跳过导入 | `account.json` 已存在 | 保持文件现状（**不会再尝试从库里补密码**） |
| B 正常导入 | 库不可读返回 `null` 以外、且 `user` 有行 | username/nickname/avatar/wallpaper/**passwordHash 原样搬运**（:101-116）|
| C 兜底 | `importFromDb()` 返回 `null`（**DB 读抛错** :83-88，或 **user 表 0 行** :89） | **写默认账户：username=`guada`、passwordHash=null、nickname=管理员**（:72-74） |

配合"跳过导入"规则，一旦走过 C，**下一次启动不会重试**，密码就永久为空（免登录）。日志会留下明确证据：

```
AccountBootstrapService  "账户文件已创建（默认账户，未设密码 → 免登录）"
AccountBootstrapService  "DB 不可读，无法导入既有账户: <错误>"
```

### 1.2 C 分支能被触发的三个现实条件（按可能性排序）

> ⚠️ 2026-10-14 更新：症状 2 已定性为**前端/索引刷新问题**（见 §2，与库和数据无关）。
> 这意味着"数据根错位/空库"不再是两个症状的共同解释，症状 1 需要独立取证——
> 下面三条仍都成立，但请以客户日志为准（`DB 不可读…` / `账户文件已创建（默认账户…` 是判别关键）。

1. **数据根指向了空的/新的库**：`detectDataPath()` 只要新布局里有（哪怕是空壳的）库就压过 AppData 真实库
2. **主库瞬时不可读/损坏**：迁移复制可能得到不完整/损坏的库（只校验 16 字节文件头，不跑 `integrity_check`）→ Prisma 首个查询即抛错 → C 分支
3. **老库缺列**（≤0.5.2 直跳）：`user` 表列自 v0.4.2 起稳定（实测 v0.4.2/v0.5.2/v0.5.6 schema 的 User 完全一致），所以这条**基本不是**账户失败的原因；缺列影响的是会话（`closed_at`）等表，已由 P0-2 修复覆盖场景 2。若客户跑的是修复前的构建，会表现为"多个域一起空"。

### 1.3 另外两条次要路径

- **文件损坏 → 以默认账户为基底改写**：`readFromDisk()` 对损坏文件返回 `null`（:220-232），随后任何资料修改走 `patch()`，基底取 `this.account ?? defaultAccount()`（:184-186）→ 写出「username=客户改的、passwordHash=null」。触发条件苛刻（文件半截写/外部改坏），但症状与报告完全一致。
- **客户自己点了"关闭密码"开关**：`GeneralSettings.vue:246-249` → `DELETE /user/password` → `clearPassword()`，**有二次确认框**，不算静默。本机 `~/.guada-dev` 的 account.json 就是 2026-10-09 14:27 被这样清掉的（导入发生在 09-18 且日志明确写了"已设密码"）——说明**迁移导入本身是会把密码带过来的**，这不是迁移缺陷。

### 1.4 结论

症状 1 **存在代码级成因**（C 分支 + 跳过导入的不可逆性），最可能的触发是 1.2-1 或 1.2-2；只有当库内 `password_hash` 为空串时才是"客户记错/本就没密码"（SQLite 层该列 NOT NULL，实测无 NULL 行）。

## 2. 症状 2：供应商「丢失」——**已定性并修复**（不是数据问题，是首启索引没刷新）

### 2.1 现象与复现（客户 + 自测一致）

升级后打开设置，供应商列表为空；**随便新增一个供应商，之前所有供应商立刻全部出现**——数据从未丢失，是内存索引在启动时读到了空目录，之后没有任何机制重新扫描。

### 2.2 根因（日志时间戳 + AppModule 顺序双重证据）

真机首次升级启动日志（`~/.guada/logs/combined-2026-10-10.log.gz`）：

```
17:49:43 ProviderFileStore          Provider file store ready ... (0 providers)   ← DI 单例先预热，目录还是空的
17:49:45 ProviderBootstrapService   Provider config migrated from DB: 10 written  ← 迁移此刻才写出 yaml
17:49:45 ProviderFileStore          Provider file store ready ... (10 providers)  ← 这是脚手架自持的另一个实例，与 DI 无关
```

链条：

1. `app.module.ts` 里 **`LlmCoreModule`（第 44 行）排在 `PersistenceModule`（第 48 行）之前**，而 NestJS 的模块钩子是**跨模块串行 await**（`@nestjs/core` `callInitHook`：`for (const module of modules) { await callModuleHook(module) }`）；
2. 于是 `LlmCoreModule.onModuleInit → ProviderFileStore.initialize() → loadAll()` 必然跑在 DB→文件导出之前，把**空目录**缓存成「0 个供应商」；
3. `9d85343b` 移除了 4 个 FileStore 的 chokidar 监听，此后**没有任何机制**在文件出现后重扫索引；
4. 直到某次写操作触发重扫——`saveProvider()` 内部 `await this.loadAll()`（`provider-file.store.ts` 的 saveProvider）——所有 yaml 才一起进入索引，表现就是「新增一个，全都冒出来」。

为什么只有供应商中招：其余域都有防护——sessions/bots/mcp/kb/account 的 store 在 `PersistenceModule` 之后初始化或走 `MetadataBootstrapGate`；AgentFileStore 所在 AgentsModule 排在 PersistenceModule 之后。**唯独 provider 域漏了门控**（`providers.module.ts` 的注释还写着"本模块在 PersistenceModule 之后初始化"，与事实相反）。

### 2.3 修复（已实施）

- `metadata-bootstrap.gate.ts`：新增 `META_DOMAIN_PROVIDERS` 域常量；
- `provider-file.store.ts`：`initialize()` 先按磁盘现状预热并**立即返回**（跨模块串行钩子下不能阻塞等门控，否则与导出互锁到超时），门控放行后**自动重扫一次**；
- `provider-bootstrap.service.ts`：注入门控，`run()` 的 `finally` 里 `complete(META_DOMAIN_PROVIDERS)`（导出失败也放行，避免每次启动空等 30s）；
- 修正 `providers.module.ts` / `app.module.ts` 里与事实相反的注释。

### 2.4 验证

- 回归用例 `test/llm-core/provider-store-gate.spec.ts`（4 例：预热早于导出→放行后自动重扫；门控已放行→直接加载；脚手架实例不等待；导出失败仍放行）；
- **真机级端到端**（真实库副本 + 空 providers 目录 + 无 marker，模拟升级首启）：

```
16:12:31 ProviderFileStore          ready ... (0 providers)
16:12:32 ProviderBootstrapService   migrated from DB: 10 written
16:12:32 ProviderFileStore          Provider index reloaded after bootstrap (10 providers)  ← 修复生效
16:12:36 NestApplication            successfully started                                       ← 起监听时索引已就绪
```

即：HTTP 服务监听之前索引已补齐，UI 不会再出现"首启空列表"。

### 2.5 对已升级客户的处理

**无需任何补救**：重启一次应用即可（第二次启动时 yaml 已在磁盘上，预热就能读到）；或者按客户自己的发现，新增一个供应商触发重扫。若客户**重启后仍为空**，才需要走 §3.1 的其它分支（marker 被空库写死 / 数据根错位 / 库损坏）。

### 2.6 历史遗留假设的处理

我在上一版文档里把症状 2 归因为"marker 在空库时被写死"——那条路径**确实存在**（`exportProviderFiles()` 读到 0 行也 `return true` 并落 marker，且 0 行时**不打任何日志**），属于同类问题的第二道隐患，但不是本次客户复现的原因。建议仍按 F2 修掉（见 §5），避免"首次运行恰好读到空库"时永久跳过导出。

### 2.2 读取侧是安全的（已排除）

- `parse()` 对缺字段宽容（`provider-file.store.ts:208-259`），只有空文档/非映射才拒；
- `listProviders()` 无过滤（:366），`GET /providers` 直接返回全部实例；
- `bundled-providers/` 已随包分发（`package.json:158-159`），打包产物里存在（实测 `release/win-unpacked/resources/backend-ts/bundled-providers`）；
- 目录解析在引导与运行期是同一套 env（`resolveDir()` :140-147），不存在"写这读那"。

### 2.3 结论

症状 2 的确定性缺陷是 **§2.1 的 marker 语义**（0 行也落 marker）+ 它依赖的 **数据根/空库问题**（1.2-1）。**供应商数据本身还在 `model_provider` 表里**，可无损恢复（见 §3.2）。

## 3. 客户机取证与立即补救

### 3.1 取证（只读，不改任何文件）

```bash
node scripts/diagnose-upgrade-state.cjs            # 自动扫描 ~/.guada、~/.guada-dev、AppData
node scripts/diagnose-upgrade-state.cjs <数据根>    # 或指定数据根
```

关键日志（按时间倒序找"首次升级那次启动"）：

```bash
# 解压历史日志也要看（升级可能发生在若干天前）
zgrep -E "账户已从 DB 导入|账户文件已存在，跳过导入|账户文件已创建（默认账户|DB 不可读，无法导入既有账户|Provider config migrated from DB|DB unreadable, skip provider migration|检测到全新安装|检测到旧版数据库安装" <数据根>/logs/*.log*
```

**一步分流**（决定根因类别，先问客户这一句）：**会话列表、消息、知识库是不是也空了？**

| 观察 | 判定 | 对应机制 |
|---|---|---|
| 只有供应商空，**重启后恢复正常**（或新增一个即全部出现） | ✅ **已定性**：首启索引预热早于迁移导出（显示问题，数据完好） | §2（已修复） |
| 会话/消息/KB **也全空**，而 `%APPDATA%\GuaDa\ai_chat.db` 有真数据 | 数据根错位 / 空库 | 1.2-1 |
| 数据都在，只有账户 `passwordSet=false` | 账户兜底路径 | 1.1 C 分支 |
| 供应商 reboots 后仍空，且「providers yaml=0 而 marker 存在」且库里 `model_provider` 有行 | 供应商 marker 被空库时写死（第二道隐患） | §2.6 / §5 F2 |
| `PRAGMA integrity_check` != ok | 库损坏 | 1.2-2 |

### 3.2 立即补救（支持人员可照做，数据可无损恢复）

0. **供应商首先试「重启一次应用」**：首启索引问题只需重启即恢复（§2.5）。若重启后仍空，再走下面第 1 条。
1. **供应商（重启仍空时）**：确认库里 `model_provider` 有行 → 停应用，删除 `<数据根>/providers/.migrated-from-db`，重启。导出是幂等的，会把缺的 yaml 全部补齐（已存在的文件不覆盖，客户在新 UI 里改过的实例不会被回退）。
2. **账户密码**：确认库里 `user.password_hash` 有值 → 停应用，删除 `<数据根>/account.json`，重启。重导会把库里的 username/nickname/avatar/wallpaper + 密码一起写回。
   ⚠️ 客户若在新版本里改过资料，先记录，重导后会以**库里的旧值**为准（可改后重启一次再手动补）。
3. **数据根错位**：停应用 → 把 `%APPDATA%\GuaDa\ai_chat.db`（连同 `-wal`/`-shm`、`file_stores`、`scheduler` 等）复制到 `~/.guada/` 对应位置 → 或删除 `~/.guada/.migrated` 与空壳库后重启，让迁移流程重新走一遍。
4. **库损坏**：优先从 `~/.guada/data/ai_chat.db.bak.*`（迁移前自动备份）或 AppData 源库恢复。

## 4. 本机实测证据（支撑上述判断）

- `~/.guada`（正式数据根）升级**成功**：迁移记录 1–5 齐全、`session=219 / message=4692 / kb_file=3`、`integrity_check=ok`、account.json `passwordSet=true`、providers `10/10` 与库内行数一致 → **正常路径不丢数据**。
- 账户导入**会**保留密码：`~/.guada-dev` 日志 `2026-09-18 12:54:48 账户已从 DB 导入（保留原密码状态: 已设密码）`；该文件的密码是 `2026-10-09 14:27` 被**显式清除**（时间与文件 mtime 吻合，`clearPassword()` 语义），不是迁移丢失。
- Prisma 脏值容忍性实测：把 `user.password_hash`、`model_provider.api_url` 置为空串，`user.findMany()` / `modelProvider.findMany({include:{models:true}})` **均不抛错**（返回空串）→ 空串不会引发整表读取失败；该列在 SQLite 层为 NOT NULL，不存在 NULL 行。
- 列演进核对：`User`、`ModelProvider` 模型自 v0.4.2 起与当前一致（v0.4.2/v0.5.2/v0.5.6 逐个 tag 核对），故老库"缺列"只可能来自 ≤v0.4.1 的库或场景 2 直跳（后者已由 P0-2 覆盖）。

## 5. 代码修复状态（按优先级）

| 优先 | 项 | 改法 | 状态 |
|---|---|---|---|
| **F0** | 供应商首启索引不刷新（本轮客户复现的根因） | provider 域补门控：预热不阻塞 + 门控放行后自动重扫（见 §2.3） | ✅ **已修复并端到端验证** |
| **F1** | 账户自愈 + 不写默认 | ①`account.json` 存在但 `passwordHash` 为空、且库里有 hash → 补导入（幂等，只补密码字段）；②`importFromDb()` 抛错时**不写默认账户**（视为未就绪，下次启动重试），仅在"库中确认无 user 行"时才写默认 | ⏳ 待定（症状 1 尚无现场证据；此前被归为 P1"设计如此"，建议本版必修） |
| **F2** | 供应商 marker 语义（第二道隐患） | 仅在「导出成功且 `dbProviders.length > 0`」或「确认全新装（库内无 user/session 行）」时落 marker；0 行时打一条显式日志（当前完全无日志）；marker 内记录导出条数供日后核验 | ⏳ 待定（防"首启恰好读到空库"永久跳过导出） |
| **F3** | 数据根与迁移安全性 | ①`detectDataPath()`：两处都有库时按「行数/大小」判定而非盲信新布局，并在可疑时告警；②`handleMigration()`：源缺失或复制任务全部落空时**不写 `.migrated`**；③复制后用 `PRAGMA integrity_check` 替代 16 字节头校验（失败则中止迁移并保留标记缺失） | ⏳ 待定 |
| **F4** | 诊断与可观测性 | 账户/供应商/会话三个引导服务的判定结果统一为 info 级显式日志（含"读到的行数"与"采用的分支"） | ⏳ 部分已有（`Provider file store ready (N)`、`Provider index reloaded after bootstrap (N)`、账户导入三态均已落日志） |

> 说明：F1 里的"不写默认账户"正是审计报告里的 P1「账户兜底」项；当时按"设计如此"保留，**现在已有客户反馈落在这一分支上**，建议升级为本版必修。

## 6. 给客户的一句话确认清单（最小信息量）

1. 会话列表/历史消息/KB 是否也空了？
2. `%APPDATA%\GuaDa\ai_chat.db` 与 `~/.guada/data/ai_chat.db` 各自大小与修改时间？
3. 数据根 `logs/` 目录打包发回（含 `.gz`）？
