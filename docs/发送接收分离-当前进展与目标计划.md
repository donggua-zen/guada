> 版本:2026-08-24 修订
> **两个方案都要做,顺序:先完整实现方案A(接收唯一 receiver),再完整实现方案B(前端会话级内容缓存)。**

---

# 方案A:接收唯一 receiver(正本:`docs/接收唯一receiver方案.md`)

## A-1 目标
前端**发送与接收分离**:
- **发送(send)**:独立入口,只调后端发起请求(`regenerationMode`/`userMessage` 只是参数),不处理事件
- **接收(receive)**:全局唯一 receiver,消费全局 SSE(StreamEventHub),所有流式事件(自己发起 / 其他窗口 / 刷新订阅)都进唯一 receiver 处理

## A-2 三条铁律
1. **唯一入口**:全项目只有一个 receiver 消费 StreamEventHub / SSE 事件,不存在第二条接收链路(`streamEventHub.subscribe` 全项目仅一处)。
2. **会话级**:receiver 按当前会话工作——当前会话事件处理,非当前会话事件丢弃(切换会话注销上一会话订阅)。
3. **时序**:receiver 必须等 `loadSession`(HTTP 拉历史)完成、拿到 `lastSeq` 基线之后才处理事件(依赖 `prevSeq >= lastSeq`)。

## A-3 落地步骤(严格按正本,一步不丢)
| 步 | 内容 | 关键产出 |
|---|---|---|
| A-1 | 新建全局唯一 `StreamReceiver` | `setActiveSession`(会话级,切换注销)+ `setHistoryBaseline(sid,lastSeq)`(时序)+ 唯一 `subscribe`(内部 `streamEventHub.subscribe`,回调按 activeSessionId 过滤) |
| A-2 | 接收唯一化(useStreamResponse) | `processStreamLoop` 事件处理注册到唯一 receiver;删除各场景各自 `streamEventHub.subscribe`;`subscribeStreamEvents` 的"触发发送"拆出归发送侧 |
| A-3 | 发送独立(sendMessage) | 新发/重答/续传/订阅参数形态统一,内部只 `apiService.chat`,不订阅、不处理事件 |
| A-4 | 时序衔接 | `loadSession(sid)` 拉历史 → `setHistoryBaseline(sid,lastSeq)` → receiver 对该会话才处理 `prevSeq >= lastSeq` 增量 |

## A-4 验收标准(全部要过)
- [ ] `streamEventHub.subscribe` / SSE 事件消费**全项目仅一处**(唯一 receiver 内部)
- [ ] 切换会话时,上一会话事件被丢弃/注销,不污染新会话
- [ ] 历史未拉取完成时事件不处理;拉取后按 lastSeq 增量正确
- [ ] 新发/重答/续传/订阅四场景事件都经唯一 receiver 处理,发送侧零事件消费
- [ ] 后端 tsc 0、前端 vue-tsc 基线一致

# 方案B:前端会话级内容缓存(方案A 完成后实现)

## B-1 目标
前端**打开过的会话内容缓存**:二次打开同一会话不再向后端重新拉取全量历史,仅靠 `lastSeq` 订阅增量补新。以一定内存换取更简化的代码实现(与 DSH 前端内存缓存 Session 一致)。

## B-2 核心模型(事件到达即改缓存,全局路由)
- **有缓存会话**(打开过):事件到达 → 唯一 receiver 按 sessionId 路由 → **直接改该会话缓存**(store 投影),响应式更新,与当前是否打开无关
- **无缓存会话**(没打开过):不建全量缓存,只暂存 **`finish` 之后**的事件(量小,未落盘增量);`finish` 之前已落盘,后端拉取必然包含,无需缓存
- **打开会话**:有缓存 → 直接用(缓存即最新投影);无缓存 → 后端拉取 + 写缓存 + 应用暂存事件

## B-3 `finish` 语义(方案B 关键)
每个 LLM 调用结束发一次 `finish`(携带 `finishReason`),**此时该轮内容已落盘**:
- `finish` 之前的事件 = 已落盘 → 后端拉取包含 → **从邮箱/暂存移除,无需前端缓存**
- `finish` 之后的事件 = 新一轮进行中,未 finish 未落盘完 → 打开会话时必须应用,否则丢 → **暂存**(量小)

## B-4 落地步骤
| 步 | 内容 | 关键产出 |
|---|---|---|
| B-1 | store 缓存层 | `SessionState.loaded` 标记(已加载,二次打开不拉)+ 会话级 LRU(上限 8,读写续期、超限淘汰)+ 每会话消息轮次上限(超出移除最旧)+ `pushTurn`(投影追加,带轮次 trim) |
| B-2 | 全局投影器 | `projectEvent(sid,chunk)`:有缓存 → `applyChunkToStore` 定位更新(复用 handle*,按 turnId/contentId 定位);无缓存 → `stashEvent` 暂存 finish 后事件;`takeStash(sid)` 打开时取暂存;stash 放**模块级**(跨 handler 共享) |
| B-3 | 打开会话应用 | `loadMessages` 二次打开短路(`loaded` → 不拉,直接用缓存);无缓存拉取成功后标 `loaded` + `takeStash`+`projectEvent` 应用暂存;seq 不连续 → `console.warn`(暂时不管) |
| B-4 | 与方案A 协调 | 事件经方案A 的唯一 receiver 到达;receiver 回调按"有缓存写缓存 / 无缓存暂存"路由(方案B 逻辑叠加在方案A 唯一接收之上) |

## B-5 验收标准
- [ ] 二次打开已缓存会话:**不重新向后端拉取**(网络请求为 0,仅订阅增量)
- [ ] 有缓存会话的事件到达即改缓存(即使未打开,响应式可见)
- [ ] 无缓存会话只暂存 finish 后事件,打开时应用不丢
- [ ] 会话 LRU 上限 8、每会话轮次上限 200,内存可控
- [ ] 与方案A 唯一 receiver 协调无冲突(发送侧零事件消费不变)
