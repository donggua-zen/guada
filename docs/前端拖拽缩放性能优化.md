# 拖拽/缩放卡顿：诊断与优化记录

记录一次前端性能排查：拖拽工作区分割条、调整窗口大小时出现明显丢帧，
且用户反馈「卡顿强度与消息数量正相关」「同一页面在 Chrome 里顺、在 Electron 里卡」。

**最终结论**：根因是**视口外回合仍在参与绘制**，成本随会话长度线性增长。
一份 DevTools trace 实测证明布局/样式根本不是瓶颈（各 0.5ms / 0.2ms），
真正吃掉帧预算的是 Paint + PrePaint；**在拖拽/缩放期间**让视口外回合跳过绘制后，
300 回合场景从 32fps 提升到 59.9fps，且滚动稳定性不受影响。

> **两次修正记录**
>
> 1. 本文件第一版把结论写成「每帧全量重排是主因」，并据此做了一批针对布局的优化。
>    用户实测反馈「没有明显改善」，随后提供的 trace 证明该判断错误——布局只占帧预算
>    的 2%。第一版中针对重排的优化保留（它们消除了真实存在的浪费，只是不是瓶颈）。
> 2. 第二版把离屏跳过写成了常驻规则，用户反馈「向上滚动内容会跳」。实测证明
>    `contain-intrinsic-size: auto` 并不能解决未渲染回合的估算问题（见第二节），
>    最终限定为「仅调整期间生效」。

## 零、trace 实测数据（决定性证据）

DevTools Performance 录制，拖拽工作区分割条期间 31 个拖拽帧的构成（中位数）：

| 阶段 | 中位耗时 | 占比 |
|---|---|---|
| **Paint** | **8.53ms** | 39% |
| **PrePaint** | **4.20ms** | 19% |
| Layerize | 1.39ms | 6% |
| 其他（输入分发、i18n 解析等） | ~7ms | 32% |
| Layout | 0.54ms | 2% |
| UpdateLayoutTree（样式重算） | 0.19ms | 1% |

关键观察：

- 单帧合计约 21.8ms → 约 46fps，与用户「明显丢帧」的体感一致；
- 拖拽窗口内 115 帧中 `STATE_DROPPED=29`、`PRESENTED_PARTIAL=25`，近一半帧未正常呈现；
- **聊天滚动层的绘制区是 1129×5312，而视口只有 1392 高——3.8 倍**。
  视口外的回合全在参与绘制，这是「和消息数量正相关」的直接原因；
- 根文档（node=2）每帧全窗重绘（2560×1392）3.5ms，490 次共 752ms，
  占 Paint 总耗时 54%——但这批重绘**主要发生在拖拽之外**（每秒 60 次，是常驻动画
  在持续重绘），不是拖拽帧的主要开销。

另一个容易误判的点：这份 trace 是在 **DevTools 已附加**的状态下录的，里面有
10785 个 `v8::Debugger` 事件与全程 CPU profiler。DevTools 本身会把 16ms 的帧拖到 21ms，
所以绝对数值偏悲观，但**各阶段的相对占比可信**。

## 一、先排除的假设（都不是原因）

### 1. 「Electron 渲染管线配置有问题」——不是

我做了对照实验：同一份合成页面（复刻应用的关键 CSS 特性：`contain`、`will-change`、
`clip-path`、`backdrop-filter`、无限 shimmer、120 个回合），分别在 Chrome 与 Electron 里
脚本化拖拽，逐帧采样。

| 场景 | Chrome | Electron |
|---|---|---|
| 40 回合 / 1400×900 | 60fps, p95 17.4ms | 60fps, p95 17.0ms |
| 120 回合 / 2560×1440 | 55.9fps, over33=8 | 55.1fps, over33=10 |
| 120 回合 + contain + will-change | 55.9fps | 54.2fps |

**两边表现一致**。GPU 状态也确认正常：`gpu_compositing=enabled`、
`rasterization=enabled`、ANGLE D3D11 走 GTX 1050 Ti、`skiaBackendType=GaneshGL`。
逐一测试 `titleBarOverlay`（透明/不透明）、`webviewTag`、`sandbox` 开关，GPU 状态均不受影响。

所以「浏览器顺、Electron 卡」不是管线差异，而是**两边实际渲染的内容不同**：
Electron 下多出 `CustomTitlebar`（`MainLayout.vue` 的 `v-if="isElectron && !isMac"`），
且真实应用窗口常是最大化（2560×1392），比随手开的浏览器窗口大得多，绘制面积差异显著。

### 2. 「每帧全量重排」——不是

见上表：Layout 0.54ms、样式重算 0.19ms，合计不到帧预算的 3%。

## 二、真正的优化：调整期间跳过视口外回合的绘制

`TurnItem.vue`：**仅在拖拽/缩放期间**给 `.turn-wrapper` 加离屏跳过：

```css
html.gd-resizing .turn-wrapper:not(.turn-wrapper--no-cv) {
  content-visibility: auto;
  contain-intrinsic-size: 800px;
}
```

### 为什么必须限定在调整期间（第一版踩的坑）

第一版把它写成了常驻规则，结果**向上滚动时内容跳动**。实测（40 个约 1700px 的回合，
滚到底后向上滚 3000px，记录 scrollHeight 变化）：

| 方案 | scrollHeight 变化 | 结论 |
|---|---|---|
| 无 content-visibility | 3556 → 3556（**0**） | 零跳动 |
| 固定 `800px` 估算 | 19297 → 6554（**-12743px**） | 严重跳动 |
| `auto 800px` | 19297 → 6554（**-12743px**） | **与固定估算完全相同** |

关键教训：**`contain-intrinsic-size: auto` 救不了这个问题**。`auto` 只能让「渲染过」的
元素记住真实尺寸，对**从未渲染过**的元素（向上滚动时即将进入视口的那些）仍然按 800px
估算。它们撑开时把视口内容整体顶走，就是跳动。这也正是代码里那条旧注释
（"800px 估算会在回合进入视口时替换成真实高度 → 内容突然被顶出去"）描述的坑，
我第一版误以为 `auto` 能绕过它。

而拖拽分割条/缩放窗口时用户**不会同时滚动**，估算值永远不会被看到。
性能收益恰好就发生在那一刻，所以把降级限定在调整期间，两头都拿到了。

### 效果（合成页面复刻，2560×1440，拖拽 2.5s，300 回合）

| 方案 | fps | p50 | over33 |
|---|---|---|---|
| 无降级 | 32.1 | 35.3ms | 59 |
| 常驻 content-visibility | 57.0 | 17.6ms | 0 |
| **仅调整期启用（最终方案）** | **59.9** | **16.7ms** | **0** |

滚动稳定性同时验证：正常向上滚动 `scrollHeight` 变化 **0**。

### 为什么条件只挂 `html.gd-resizing`

`useResizeActivity` 的调整态已覆盖全部三条入口——拖分割条、拖侧栏把手、窗口缩放——
不需要再区分。它还带 150ms 尾延迟，松手后不会立刻恢复，避免最后一帧抖动。

### 配套修复：`scrollToMessage` 不再依赖 `offsetTop`

`ChatPanel.vue` 原先用 `targetElement.offsetTop` 定位。实测加上 `content-visibility` 后，
未渲染回合的 `offsetTop` 会从 2180 变成 20920（按 800px 估算累加，差近 10 倍）。
虽然现在只在调整期启用、大纲跳转通常发生在非调整期，但仍改成更稳妥的口径：

```ts
const targetTop = container.scrollTop + driftToTarget()
container.scrollTo({ top: Math.max(0, targetTop), behavior })
```

后续的多轮落点校正本来就用 `getBoundingClientRect`，两者口径一致。

**A/B 开关**：`localStorage['gd:turn-cv']='0'` 后刷新可关闭（与 `gd:lazy-turns` 同一套约定）。

## 二·补、拖窗口不生效的 bug（已修）

第一版实现里，`useResizeActivity()` 负责绑定 window resize 监听，但**全项目没有一个
组件调用它** —— 所有消费方只 import 了 `beginResizeActivity` / `isResizeActivityActive`。

后果：拖分割条正常（`GdSplitpanes` 直接调 `beginResizeActivity()`），
**拖窗口却完全不降级**，`gd-resizing` 从不挂上。这解释了用户反馈的
「直接拖拽分割暂时没问题，但是直接拖拽窗口本身还是会有性能问题」。

修法：`bindWindowResize()` 改为**模块加载时自动执行**，不再依赖调用方记得触发。
本模块本身就是全局单例状态机，绑定 window 监听是它的固有职责。

已加回归测试（`useResizeActivity.test.ts` 的「模块加载即绑定 window resize」），
用 `vi.resetModules()` + 仅 import 来锁住这个行为——它验证的正是「不调用任何导出函数，
监听也已注册」。

### 关于「拖窗口」剩余的卡顿

修完上述 bug 后仍可能有残余卡顿。我用合成页面做了对照（300 回合、内容与真实应用同构、
带 `titleBarOverlay`）：

| 场景 | fps | p95 |
|---|---|---|
| 真实窗口 `setSize` 驱动 | 60 | 16.9ms |
| 仅改内容宽度（不触发窗口 resize） | 60 | 16.9ms |
| 空白页 + 窗口缩放 | 60 | 16.9ms |

**在合成环境里复现不出窗口缩放的额外开销**，说明它来自真实应用独有的因素。已知
候选（按可能性排序）：

1. **侧栏自动收起**：窗口宽 < `SIDEBAR_AUTO_COLLAPSE_WIDTH`(1024) 时
   `stores/layout.ts` 会切换 `sidebarAutoCollapsed`，整棵布局重排 + 侧栏显隐过渡。
   这是**离散的、比拖分割条重得多**的一次变化。拖到 1024 附近来回晃会反复触发。
2. **`container-type: inline-size` 容器查询**：`ChatPage.vue` 的 `.chat-pane-content`
   与 `ChatInput.vue` 的 `.input-area` 都在宽度变化时重算 `@container` 规则。
3. **主题壁纸层**：qi-dusk 的四层背景用视口百分比尺寸 + `cover`，窗口每变一帧都要
   重新栅格化约 700KB 位图（见第四节）。
4. **`Avatar` 的 `container-type: size`**：无头像时占位符用 `60cqw` 字号，尺寸包含
   需要重算（影响面小，每条助手消息一个）。

要精确定位需要在**真实应用 + 真实后端**下录 trace。自动化驱动真实应用在这台机器上
不稳定（自建 main 缺 IPC 处理器、CDP 与 UI 争用），建议手动操作时用 DevTools 的
Performance 面板录一段窗口缩放，重点看 `Layout` / `PrePaint` / `Paint` 的占比，
与本文第零节的拖拽数据对比。

## 三、其他已做的优化

以下优化针对第一版误判的「重排」方向，**不能解决主问题**，但它们消除的都是真实存在的
每帧浪费，保留：

1. **全局「调整中」态**（`composables/useResizeActivity.ts`）

拖分割条、拖侧栏把手、缩放窗口统一进同一个开关，给 `<html>` 挂 `gd-resizing`：

- 引用计数：嵌套分割条各自持有，内层结束不会误释放外层；
- 尾延迟 150ms 释放：窗口缩放会连续派发大量 resize 事件，立即清会让下游工作在下一次
  事件里又跑一遍；
- 自带 `window.resize` 监听（rAF 合并），调用方无需各自接线；
- **布尔值与 DOM class 同源同刻**：若布尔值提前翻回 false，组件会先恢复工作、CSS 却还在
  压制动画，出现「动画停了但重活又开始了」的半吊子状态。

CSS 侧（`style.css`）在 `html.gd-resizing` 下：


- 暂停无限动画（`animation-play-state: paused`）：shimmer 占位线、思考点阵、spin、pulse；
- 关掉 `backdrop-blur-xl` 的 `backdrop-filter`。

选择器全部写具体类名而非 `*`——全局通配会在切换瞬间让整棵样式树失效重算，
反而制造一次长任务。

### 2. 清掉每帧的级联工作

| 位置 | 原问题 | 处理 |
|---|---|---|
| `SidebarLayout.vue` | 每帧 emit → `layoutStore.setSidebarWidth` → `useStorage` **每帧同步写 localStorage 并派发 StorageEvent** | 拖拽走本地 `liveWidth`，mouseup 提交一次（照搬 `FloatingChatPanel` 既有做法） |
| `ChatPanel.vue` | 拖拽期用 `!important` **重新打开** `.aside-bleed-col` 的 `flex-basis` 过渡 → 每帧布局动画，直接抵消 `GdSplitpanes` 的过渡屏蔽 | 整体移除该豁免 |
| `ChatPanel.vue` | 每次内容 resize 都 `mountVisiblePlaceholders()`（对全部占位做 `getBoundingClientRect()`） | 调整期跳过；稳定后尾帧自然补一次 |
| `GitChangesPanel.vue` | `ResizeObserver → diffSplitPct → 内层 GdSplitpanes` 的每帧往返 | 给 `GdSplitpanes` 加**像素模式**（`pane2Px` / `minPane1Size`），整条换算链删除 |
| `TerminalPanel.vue` | 每帧 `fitAddon.fit()` + 给 PTY 发 resize | 150ms 防抖，调整期直接跳过 |
| `BrowserPreviewPlaceholder.vue` | 每帧读 rect 写 store → webview 每帧重算 `transform: scale()` | 调整期跳过，稳定后补一次 |
| `BrowserWebviewLayer.vue` | 每个 resize 事件都写 reactive ref | rAF 合并 |
| `GlobalSidebar.vue` | resize 回调做 `offsetWidth/offsetLeft`（强制同步布局），轨道未挂载时也执行 | rAF 合并 + 未挂载短路 |
| `ChatPage.vue` | `onPaneResize` 每帧 `setDragging(true)` | 首帧守卫 |

### 3. `GdSplitpanes` 像素模式

新增 props：`pane2Px`（给定数字即进入像素模式，pane2 定宽、pane1 吃剩余）、
`minPane1Size`；新增 emit `pane2-resized`。

边界约定（`splitpanesMath.ts`，有单测覆盖）：

- `pane2Px <= 0` 是**收起**信号，必须绕过 `minPane2Size`——否则最小宽会把 0 顶回来，
  「收起右侧栏、左侧占满」永远失效；
- 容器放不下时优先保证 pane1 最小宽，pane2 让位；
- 结果恒满足 `p1Px + p2Px === 容器宽 - 1`，不留缝不溢出；
- 折叠态单独映射：像素模式下 pane2=0 才是收起（百分比模式是 splitSize=100）。

### 4. 修掉 qi-dusk 下的 backdrop-blur 遗留

`theme-runtime.ts` 切到 `ownsBackground` 主题时只清了 `--wallpaper-image`，没清
`layoutStore.wallpaperUrl`（那是「切回默认主题该恢复什么」的唯一真相，不能清）。
于是 `ChatPanel.vue` 的 `hasWallpaper` 仍为 true → 输入框继续挂 `backdrop-blur-xl`（24px），
压在主题画布上每帧重算模糊。

修法：`theme-runtime` 导出响应式 `themeOwnsBackground`，`hasWallpaper` 改为
「store 有壁纸 **且** 主题未接管背景」。

## 四、主题层建议（未实施，待决定）

qi-dusk 在 git 里仍是未提交状态，改动会混进皮肤工作，故只给建议：

1. **四层背景画布**（`qi-dusk.css` 的 `body::before`）用 `auto 71.3% / 81% / 88%` + `cover`，
   窗口每帧改变渲染尺寸 → 每帧重新栅格化约 700KB 位图。
   建议改为固定像素尺寸 + `transform: scale()`（变换走合成器，不重栅格化），
   或整体收成一张预合成大图。
2. **每张消息卡 `clip-path`**：建议在 `html.gd-resizing` 下 `clip-path: none`
   （该 class 已由本次改动提供）。
3. **输入坞 9 层背景 + 203KB PNG 拉满 `100% 100%`**：建议拖拽/缩放期间降级为纯色。
4. `style.css` 全屏壁纸的 `cover` 重栅格化是应用层与主题共有的成本，
   要处理需改壁纸层实现方式，风险较高，建议单独立项。

## 五、如何度量

仓库自带 opt-in 统计（见 `docs/frontend-perf-profiling.md`）：

```js
localStorage.setItem('gd:perf','1')   // 重启
__gdPerf.reset()
// 拖 3 秒分割条 / 缩放窗口 3 秒
__gdPerf.report()                     // fps / longTasks / longTaskMs / domNodes
```

优化前后用同一长会话、同一操作对比。也可以直接看 `<html>` 上是否出现 `gd-resizing`
（拖拽时应出现、松手 150ms 后消失）。

### 用 DevTools trace 定位（本次用的方法）

1. Performance 面板录制，拖拽分割条 3-5 秒；
2. 在 trace 里看 **Paint 事件的 clip 区域**——这是判断「是否在画视口外内容」最快的手段。
   正常情况绘制区高度应接近视口高度；本次实测是视口的 3.8 倍，直接暴露了离屏回合问题。
3. 对比 `Layout` / `UpdateLayoutTree` / `Paint` / `PrePaint` 的耗时占比，
   不要凭直觉假设瓶颈在布局。

> 注意：录制时 DevTools 附加本身会带来可观的额外开销（本次 trace 里有 10785 个
> `v8::Debugger` 事件），绝对数值偏悲观，但相对占比可信。

### A/B 对照开关

```js
localStorage.setItem('gd:turn-cv', '0')   // 关闭离屏跳过，刷新后生效
localStorage.removeItem('gd:turn-cv')     // 恢复默认（开启）
localStorage.setItem('gd:lazy-turns', '0') // 关闭懒挂载
```

## 六、验证清单

- 拖拽分割条时文字仍逐帧重排（未冻结），鼠标不丢帧；**300 回合以上的长会话**是
  关键验证场景（短会话在优化前也接近满帧，看不出差别）；
- **滚动长会话时无内容跳动**——这是第一版踩过的坑，务必验证：向上滚动经过
  未渲染的回合时不应有位移（实测判据：滚动过程中 `scrollHeight` 不变）；
- 大纲/引用跳转落点正确（`scrollToMessage` 已不再依赖 `offsetTop`）；
- 展开/收起思考分组、图片加载后滚动位置稳定；
- 窗口缩放（qi-dusk 与默认主题各一次）不丢帧；
- 工作区分割条位置刷新后保持（`workspaceSplitSize` 仍只在 mouseup 落盘）；
- 侧边栏宽度拖拽后刷新保持（落盘时机变了，但仍是 mouseup）；
- Git 面板拖拽后目录宽度保持，窗口缩放时目录像素不变；
- 终端面板缩放后 PTY 尺寸正确（松手后补一次 fit）；
- 浏览器预览位置/缩放正确，拖拽期间不截获鼠标；
- 工作区全屏/折叠切换、概览面板自动折叠阈值行为不变。
