## 1. P0-1 知识库向量对齐失败

**问题**：`kb-migration-bootstrap.service.ts` 的 `attachVectors` 用 `vectors.get(row.id)` 对齐，而旧向量库键是 `chunk_<idx>_<fileId>`、旧 `kb_chunk.id` 是 cuid（实测命中 0/411，`vector_id` 命中 403/411）。

**修法**（三层匹配，逐层回退，全部命中数进日志）：

1. `row.vectorId`（旧库 `vector_id` 列，权威键）
2. `row.id`（新管线/文件形态下两者相同）
3. 重建键 `chunk_${chunkIndex}_${itemId}`（`vector_id` 为空的历史数据兜底）

**涉及**：`backend-ts/src/common/database/bootstrap/kb-migration-bootstrap.service.ts`（`attachVectors`）

**验证**：
- 新增回归用例：S1 fixture 使用 `id=cuid` / `vectorId=chunk_0_item-1`（真实形状），断言向量落到 chunk 行；
- 真机脚本：用老库 + 老 `vector_db.sqlite` 断言对齐率 100%。

**回滚**：单函数改动，可独立回退；旧向量库文件始终保留（`.pre-sqlite`）。

**关于「已升级用户」**：该缺陷只存在于**未发布的开发提交**（v0.5.6 没有 `kb-migration-bootstrap`），出货用户的数据未受影响，因此不需要补救 CLI。仅当有人跑过中间构建时才有意义——那种情况下原始向量仍在旧向量库文件里，可按「重建键 `chunk_<idx>_<itemId>`」回填，无需重新调用嵌入模型。

## 2. P0-2 旧库（≤0.5.2）升级空转

**问题**：`migration-runner.service.ts` 场景 2 把 0002–0005 标记为已应用但不执行。旧库缺 `closed_at` 等列，新 Prisma schema 全列 SELECT 直接报错 → 会话不导出、消息不迁移。

**修法**（保持场景 3 完全不变，风险隔离）：

1. 新增 `legacy-schema-reconcile.ts`：以 `0001_baseline.sql` 为唯一真源（在内存库执行后读 `PRAGMA table_info`），对旧库做**加列/补表**：
   - 缺表 → 用基线的 `CREATE TABLE` + 该表索引补齐（含外键，执行时关 `foreign_keys`）；
   - 缺列 → `ALTER TABLE ADD COLUMN`（类型/非空/默认值取自基线）；
   - 非空且默认值为非常量表达式（如 `CURRENT_TIMESTAMP`）的列无法 ADD → 降级为可空并告警。
2. 场景 2 改为：备份 → schema 对齐 → 执行 pending 迁移 → 记录。日志明确打印「旧版库：已对齐 N 列/补 M 表，执行 K 个迁移」。
3. `0002_add_session_closed_fields` 幂等化：逐条 `ALTER`，按 `PRAGMA table_info` 判断列是否已存在（同时消除「记录写入失败后重跑报 duplicate column」的隐患）。
4. 附带修复：旧库 `file.message_id` → `content_id` 回填（仅当旧表存在 `message_id` 且 `content_id` 为空时；按所属消息的 user 内容优先、否则最早内容）。该列随后会被 0005 重建表丢弃，不回填则老附件在消息迁移中失联。

**涉及**：`migration-runner.service.ts`、新增 `legacy-schema-reconcile.ts`、`migrations/0002_add_session_closed_fields.ts`（+ 删除其 .sql）

**验证**：
- 合成老 schema 用例（含会话数据）：升级后列齐、行数据保留、去外键生效（可写入文件侧 id）、`_app_migrations` 完整、重复执行不报错；
- 真机实测：用 `~/.guada/data - 副本/ai_chat.db`（7 月老库，缺 7 列）副本跑升级，断言会话/消息可读、`closed_at` 存在。

**回滚**：迁移前自动备份（沿用 `.bak.<ts>`，本次为场景 2 也开启备份）。

## 3. P2 内置主题不随包分发

**确认**：`docs/plugin-theme-registration-plan.md` 已记录该缺口（2026-09-02）。实测复核：

- `package.json` 打包清单（`files` / `extraResources`）不含 `plugins/`；
- 生产 spawn env 只注入 `PLUGINS_USER_DIR`（安装后为空），不注入内置插件目录；
- 插件入口是 `index.ts`，生产 `node dist/main` 无 TS loader；且入口 `import "../../backend-ts/src/modules/plugins"` 在打包后（只有 dist）无法解析。

结论：**打包版主题确实只剩 default**。修复：

1. 插件入口改为**无依赖的 CommonJS `index.js`**（普通类即可：`PluginBase` 无必需成员，loader 已支持「CommonJS 直出类」），`manifest.main` 指向 `index.js`；
2. 新增内置插件目录扫描来源 `builtin`（env `PLUGINS_BUILTIN_DIR`），**优先于 user/dev 扫描**（`category=system` 的官方插件不被用户副本遮蔽）；
3. 生产 spawn env 注入 `PLUGINS_BUILTIN_DIR=<resourcesPath>/plugins`；`extraResources` 增加 `plugins/guada-themes → plugins/guada-themes`；
4. 文档更新：`plugin-theme-registration-plan.md` 缺口章节标记为已修复。

**验证**：新增用例用真实 `plugins/guada-themes` 目录经 `ExternalPluginLoader.loadExternalPlugin`（source=builtin）加载，断言 11 个主题注册 + 每个 `cssFile` 在磁盘存在；`electron-builder --dir` 后检查 `resources/plugins/guada-themes` 与 `index.js` 存在（打包环境验证）。

**回滚**：删 `extraResources` 项与 env 注入即回到现状（dev 不受影响）。
