Storage Architecture Redesign · guada · 2026-09-16

存储架构重设计
哪些上库、哪些留文件

基于三个已安装参照产品的一手证据（Codex 数据目录的 7 个 SQLite 全量 schema 只读提取、DeepSeek Harness 源码走读、AutoClaw/OpenClaw 磁盘与文档验证），为 guada 的三种目标形态（端侧 70% / B-S 20% / 企业 10%）给出分域存储决策与架构设计。

参照证据codex（Rust + sqlx-sqlite）· dsh（TS monorepo）· openclaw（TS gateway）
方法只读 schema 提取 + 源码走读 + 文档交叉验证
关联architecture-audit · repo-layer-design（前两篇）
VERDICT

不做"全文件"也不做"全库"——维持"文件为权威 + SQLite 为派生索引"的混合架构，三家参照全部如此。具体分界：事件流（会话消息）与用户可见实体（角色/供应商/配置）留文件；检索（跨会话搜索）用可重建的 SQLite 派生索引；知识库维持每库一个 kb.db（唯一"库做权威"的例外）；运行时状态机（日志/队列）个人版留文件、企业版上库。企业版通过存储后端契约接入 Postgres，不推翻个人版存储栈。

Codex（OpenAI）

  • 会话索引 = SQLite：state_5 的 threads 表存 rollout_path（36 行，文件是权威）

AutoClaw / OpenClaw
TS gateway · 文件最彻底 · 唯一记忆库

  • 索引 = 单文件：sessions.json（channel→sessionFile 映射）
  • 删除/重置 = 文件改名：.jsonl.reset.<ts> 后缀，无库参与
  • 记忆检索 = 唯一 SQLite：per-agent 库，FTS5 + 向量 + CJK trigram + 可选 sqlite-vec

  • workspace = 纯 Markdown：AGENTS/SOUL/USER/MEMORY.md 用户直改

Codex 的"投影水位线"——文件与库关系的教科书实现

权威层（文件）append-only，不可变
rollout-*.jsonl（sessions\2026\08\26\）——对话事件的唯一真相。threads 表的 rollout_path 列指向它；删除/迁移以文件为准。
目录层（state_5.sqlite）threads · 36 rows
会话清单：id / rollout_path / cwd / title / sandbox_policy / approval_mode / tokens_used。这是"meta 索引"，从 JSONL 迁移而来（session_index.jsonl → threads 表，8 月完成）。
投影层（thread_history_1.sqlite）item_json + byte_offset
thread_items(665) / thread_turns(78) 从 JSONL 折叠而来，thread_history_projection_state.next_rollout_byte_offset 记水位——库是文件的增量投影，可回填可重建（backfill_state + rollout_migration_state 两个迁移状态机佐证）。
运行时层（独立小库 ×4）logs / queue / goals / memories
每个关注点一个库 + 分代号文件名（logs_2 / state_5 / goals_1）= schema 代际版本化；logs_2 有 2100 行——多进程常驻场景（WAL 并发）才需要库做日志。

三家共性结论：① 会话正本 3/3 用 JSONL 文件；② 配置实体 3/3 用可读文件；③ 检索 3/3 用 SQLite 派生索引（dsh 甚至默认关闭）；④ 差异只在"运行时状态"——codex 多进程常驻所以上库，单进程产品（dsh/openclaw/guada）留文件即可。

02

决策框架：六个判据

NOT "DB VS FILES" BUT ACCESS PATTERNS

判断一个域用什么介质，不问"它重要吗"，问六个问题——每个判据都直接对应三家参照的做法：

写模式append-only 顺序写 vs 随机更新/事务→ 事件流归文件，状态机归库
查询模式按 id 直取 vs 组合过滤/FTS/向量→ 直取归文件，检索归派生索引
规模<1 万条 vs 更大→ 小数据内存索引（233 会话 0.7-1.2s 已实测）
用户可见性要不要让用户手改/备份/进 git→ 产品属性，三家全把配置留成文件
并发单进程单写者 vs 多进程/多租户→ codex 上库的根因；guada 单写者无需
一致性单记录原子写 vs 跨记录事务→ tmp+rename 够用归文件；需要事务归库

关键认知：kb.db 已经是"判据全中"的正确上库案例（FTS+向量+分块=查询密集；删除库=重建=爆炸半径可控）。问题从来不是"要不要数据库"，而是"哪个域的访问模式值得付库的复杂度税"。

核心判断

guada 现在的存储架构方向与三家参照完全一致，不需要推翻。真正要做的只有三件事：① 跨会话搜索补一个"派生 SQLite 索引库"（照 codex 投影水位线或 dsh 默认关闭模式）；② 把崩溃语义补齐到 dsh 水准（每批 fsync + 撕裂尾恢复——JSONL 模式可靠的真正来源）；③ 为企业版预留存储后端契约（见 05 节）。

04

统一架构与三形态

ONE STACK · THREE SHAPES

统一分层（三形态共享）

领域层domain
会话/角色/知识库等业务模型与流程——完全不感知介质。
Store 层per-domain stores
每域一个 Store：领域动词 + 缓存 + 原子写 + 启动门控。这就是持久化的全部词汇（见 repo-layer-design 篇）。
介质实现backends
文件（json/yaml/md/jsonl——权威）· SQLite（kb.db 权威例外 + 搜索派生索引）· Postgres（仅企业版）。
索引/投影derived
跨会话搜索索引：从权威文件增量投影（水位线），可删可重建可默认关闭——与权威的写入路径解耦。

三种形态，一个存储栈

端侧个人版
ELECTRON · 70%
存储栈
文件权威 + 内嵌 SQLite（kb.db + 可选搜索索引）。零运维、可备份、用户可读。
并发模型
单进程单写者（writeChains 互斥已足够）。
要做的
补 JSONL 崩溃语义（fsync/撕裂恢复）；跨会话搜索索引做派生可重建。
极客 B/S 版
DOCKER / SELF-HOST · 20%
存储栈
与端侧完全相同——dsh 已验证 cli/web 同构可行：web 只是传输层（HTTP+WS 桥接同一 host 进程）。
并发模型
仍是单实例单写者；数据根挂 volume（USERDATA_DIR 环境变量已就绪）。
要做的
无。现有架构天然支持——这正面回答了"B/S 要不要上数据库"：不需要。
企业版
CLOSED SOURCE · 10%
存储栈
个人版栈 + Postgres 后端（多租户域换实现）+ 对象存储（附件/原件）。
换库的域
会话索引与搜索（跨租户查询）、用户/组织/权限、审计日志（合规查询）、中央知识库（pgvector）。
不换的域
角色/供应商模板仍文件分发（bundled-* 模式），安装期导入。

三形态共用同一领域层与 Store 接口——企业版的"基座"意义正在于此：只换介质实现与多租户壳，业务逻辑零分叉。

05

企业版剥离策略

OPEN CORE BOUNDARY
开源核心OPEN CORE
领域层 + Store 接口 + 文件/SQLite 实现。这是个人版全部，也是企业版的基座。license：Apache-2.0 或 AGPL（视商业化策略；AGPL 对闭源竞品更有威慑）。
闭源企业包ENTERPRISE OVERLAY
Postgres Store 实现 ×N（会话索引/用户/审计/中央 KB）+ 对象存储适配 + 多租户壳（org/租户上下文注入）+ RBAC/SSO/审计 UI + 管理控制台 + 升级与迁移工具。
  • 以 npm 私有包 / 独立 repo 分发，构建期与核心合并——核心不感知企业包存在（依赖方向单向：enterprise → core）
  • 租户上下文作为 Store 方法的显式参数（个人版传常量单租户），不污染领域层
契约时机WHEN TO ABSTRACT
现在不抽接口（避免 repo-layer-design 篇说过的形状税）；企业版立项时抽——那时 Postgres 实现是真实存在的第二个实现，接口由两个实现的最大公约数自然长出，而不是想象出来的。dsh 的 StorageBackend 契约（KvFacet + version 戳 + layout + 按域路由）是现成的蓝图。
多租户的本质差异

企业版不是"个人版 + 更多用户"——它是并发写者 + 跨记录事务 + 合规查询三者的组合，恰好全部落在数据库的能力域。这就是为什么"以个人版为基座"成立：基座提供领域模型与文件优先的默认实现，企业版把判据命中"并发/一致性"的域换成库实现，其余原样继承。
