## 0. 已确认决策

| # | 决策 | 依据 |
|---|---|---|
| 1 | **入口仅用户开启**，模型不注册 `EnterPlanMode` | 用户明确约束；主动能力预留（§12） |
| 2 | **计划模式自带强制只读**，但**不改写** `sandboxMode` | 用户选择。语义最强，符合"计划模式"的承诺；状态仍与安全档位正交 |
| 3 | 计划产物落盘 `.guada/plans/plan-<sessionId>.md` | 与 `.guada/tools_output/` 同族，不污染用户源码目录；压缩后重注入有稳定来源 |
| 4 | 完整提醒**按计划周期落库一份**，后续迭代稀疏临时注入 | 解决"第二次工具往返后完整指导消失"；审计可见；仍不改 system，保留 KV 前缀 |
| 5 | 首期 = 后端闭环 + 前端最小开关 | 可端到端验证；计划卡美化/侧栏/目录二期 |

**核心架构立场**：计划状态是**与权限档位正交的独立布尔 `planEnabled`**，不是 `SandboxMode` 的第四个取值。`SandboxMode` 管文件效应的强制力，`planEnabled` 管协作状态——两者不共用词表、不互相改写。这是 ZCode 用 `ExecutionState { mode, planEnabled }` 二元组给出的结构，也是 `安全模式三档方案.md` §4 对 DSH 的判断。

## 1. 状态模型

- `session.settings.planEnabled: boolean`（会话级持久化，默认 `false`）
- `session.settings.planModeEpoch: string | null`（计划周期；每次进入计划模式生成新值，完整提醒按周期只落一份）
- **逐消息冻结**：`user/message` 的 `metadata.planEnabled` 随消息落库，对齐 `sandboxMode` 的现有做法（`jsonl-session-context.ts:519-525`）。每轮按**接纳那一刻**的计划态解释；队列中的消息不因用户后续切换而改语义
- **归一化发生在接纳边界**，不在消费时（ZCode `resolveExecutionState` 的注释："不能在队列消费时按当前配置重新解释"）
- 运行时读法：`ISessionContext.getPlanEnabled(): boolean`

与 `sandboxMode` 的对照：

| | `sandboxMode` | `planEnabled` |
|---|---|---|
| 语义 | 文件效应强制力 | 协作状态 |
| 词表 | `read-only` / `workspace-write` / `danger-full-access` | `boolean` |
| 谁改 | 用户 | 用户（开启）；模型（仅可关闭，经审批） |
| 是否互相改写 | **否** | **否** |

## 2. P0 工具能力元数据（地基）

**这是本项目当前最大的缺口**：`ToolDefinition` 只有 `{ name, description, parameters }`，权限门没有可依据的能力声明。

### 2.1 新增字段

`ToolHandlerDef`（`backend-ts/src/modules/plugins/types/plugin.types.ts:171-204`）新增：

| 字段 | 语义 | 缺省 |
|---|---|---|
| `readOnly?: boolean` | 只读执行能力——计划门的**唯一**依据 | `false` |
| `allowedInPlanMode?: boolean` | 计划态逃生舱（少数需放行的非只读工具） | `false` |

**不与 `dangerLevel` 合并**：`dangerLevel` 是风险展示语义，且当前**零消费者**（全仓 grep 只有声明与赋值，无任何读取），与"执行能力判定"是两回事。合并会埋语义债。

### 2.2 三处注册 API 同步

| 位置 | 文件 |
|---|---|
| `PluginApi.registerTool`（Zod 分支 + legacy 分支） | `modules/plugins/api/plugin-api.ts:44-78` / `:213-315` |
| `Toolkit.registerTool` / `registerRawTool` | `modules/plugins/toolkit/toolkit.ts:39-182` |
| `ToolKitHandle.registerTool` 类型声明 | `modules/plugins/types/plugin.types.ts:251-262` |

### 2.3 存量工具标注清单

**`readOnly: true`**（16 个）
`read` `glob` `grep` `tool_learn` `get_current_time` `web_search` `web_parser` `image_recognize` `image_view` `kb_search` `kb_list_files` `kb_get_chunks` `doc_parse` `doc_batch_parse` `scheduler_list_tasks` `skill_learn`

**`allowedInPlanMode: true`**（5 个）

| 工具 | 理由 |
|---|---|
| `todo` | 计划阶段维护待办有助于计划成型（对齐 ZCode 把 `TodoWrite` 列入只读集） |
| `browser_run` | 只影响临时调研环境，不触碰用户工作区与系统资产；旧 `browser_*` 扁平工具已退役，浏览器调研统一走这里 |
| `subagent_spawn` `subagent_manager` | 派子代理做调研是计划阶段的正道（子代理**不继承** `planEnabled`，见 §8 的已知风险） |
| `ExitPlanMode` | 自身即逃生舱——避免为它写特判分支（ZCode 需要单独的转换策略，本方案不需要） |

**保持缺省 → 计划态被拒**
`write` `edit` `run_command` `process` `kb_add_document` `scheduler_create_task` `scheduler_delete_task` `scheduler_toggle_task` `workflow_run` `remote_transfer` `send_file` `clear_session`

**MCP 动态工具：默认拒绝**（`registerRawTool` 不传 `readOnly` → 缺省 `false`）。无法判定外部工具的破坏性。ZCode 在此处的 `permissionName === 'mcp'` 宽判定是**已知的坑**（其研究报告 §9），不照抄。

## 3. P1 权限门

### 3.1 插入点

`ToolExecutor.executeTool`（`backend-ts/src/modules/tools/tool-executor.service.ts:151-212`），**紧跟 `toolScope` 检查之后**（`:175-191`）、Zod 校验之前。

这是**唯一 choke point**：主循环经 `executeBatch`、影子轮次、`tool_use` 懒加载再入口，全部回落到此。

### 3.2 判定顺序

```
if (!session.getPlanEnabled())  → 跳过（非计划态零开销）
if (capability.allowedInPlanMode) → 放行
if (capability.readOnly)          → 放行
if (isSubAgentSession && !capability.readOnly) → 拒绝   // 子会话短路：逃生舱不生效
否则 → 拒绝
```

**拒绝形态**：返回 `isError: true` 的 tool-result（**非抛错**），照抄 `toolScope` 的既有形态：

```
Plan mode is active: only read-only tools are available. This tool cannot run until the user approves the plan and exits plan mode.
```

**子会话短路**的理由：子代理若调用 `ExitPlanMode`，审批卡会挂到用户看不见的子会话上，**卡死父回合**（ZCode 为此在所有子代理工具面强制剔除两个 plan 工具，注释写明"子代理没有独立的 plan approval 恢复面"）。本方案用一条门规则覆盖，比工具面剔除更内聚。

### 3.3 `run_command` 在计划态下的处理

- 以 `sandboxForMode('read-only')` 执行（**无视**会话的 `sandboxMode`）
- 提权参数（`sandbox_permissions` / `justification`）**直接报错**：`"sandbox_permissions is unavailable in plan mode. Exit plan mode first if a write is required."`

**为什么不用命令白名单**：白名单无法穷尽，会误拒合法只读命令（ZCode 的 `isRuntimeReadOnlyBashCommand` 是一份需要持续维护的清单）。靠沙盒强制更可靠，且模型仍能跑 `git status` / `ls` / `grep` 完成调研。

**注意**：计划模式下 `run_command` 必须**声明 `readOnly: true`**，否则会被 §3.2 的门拒掉。它的只读性由执行期沙盒保证，不由声明保证——实现时需在 handler 内读 `session.getPlanEnabled()` 决定沙盒档位。

### 3.4 与 ZCode 的差异（刻意的简化）

ZCode 需要为"用户交互类工具"写专门的优先级排序（`requiresUserInteraction` 必须早于计划门），因为它的审批工具与写类工具同源。本方案不需要：`ExitPlanMode` 已是逃生舱，`write`/`edit` 的提权路径被门挡住即正确。

## 4. P2 `ExitPlanMode` 工具

### 4.1 契约

- 名称：`ExitPlanMode`
- 描述语言：**英文**（已核实现有工具描述为英文，`%key%` 占位符 + 英文正文）
- `inputSchema`：`{ plan: string }`——1..20000 字符，`.refine(v => v.trim().length > 0)`
- **本期不收 `allowedPrompts`**：ZCode 自己都没消费它（其研究报告 §9 点名的死参数），列为预留

工具描述（供实现直接使用）：

```
Use this tool when you are in plan mode and have finished writing your plan and are ready for user approval.

## How This Tool Works
- You should have already explored the codebase and finalized the plan you want the user to review.
- This tool takes the plan content as its required `plan` parameter.
- Pass the complete plan in the `plan` field; the user will review that content before approving implementation.
- The user will see the contents of the `plan` parameter when they review it.

## When to Use This Tool
Only use this tool when the task requires planning the implementation steps of a coding task. For pure research tasks — gathering information, searching files, reading files, or generally understanding the codebase — do NOT use this tool.

## Before Using This Tool
Ensure your plan is complete and unambiguous:
- If you have unresolved questions about requirements or approach, ask the user before finalizing your plan.
- Once your plan is finalized, use THIS tool to request approval.
```

### 4.2 handler 流程

```
1. !session.getPlanEnabled() → isError "Not in plan mode. This tool is only for exiting plan mode after writing a plan."
2. 落盘 <workspace>/.guada/plans/plan-<sessionId>.md
     - 原子写 + createParents
     - 失败即中止（不翻转状态）；计划为空白 → 报错
3. askService.ask(session, {
     kind: 'approval',
     title: '计划审批',
     toolCallId, toolName: 'ExitPlanMode',
     questions: [{ id: 'plan', question: '是否批准该计划并开始实施？',
                   detail: plan,                    // 计划全文进卡片
                   options: [{ label: '批准' }, { label: '拒绝' }] }],
   }, abortSignal)
4. 批准 → 翻转 planEnabled=false + 写事件 + 返回 { approved: true, plan }
5. 拒绝 → 见 §5
```

**用 `ask()` 而非 `requestApproval()`**：后者拒绝即抛 `AskDeniedError`，拿不到"有无用户文本"的区分，而我们需要它决定走哪条拒绝路径。

**审批卡复用**：`SessionCards.vue` 已渲染 `kind: 'approval'` 且 `detail` 会展示，**零前端改动**。

### 4.3 状态翻转与事件

翻转必须**先落盘、后改状态**（ZCode 的教训：`persistExecutionState` → `runtime.config`）。写两条：

1. JSONL 事件 `session/mode_changed`（审计 + 重放）
2. stream 帧 `plan_mode_changed`（驱动前端与多窗口同步）

## 5. 拒绝闭环

### 5.1 评估结论（应你要求做的对比）

你的方案 = **有用户文本 → 工具结果表达拒绝 + 追加真实用户消息；无文本 → 仅工具结果**。
对照方案 1 = 统一走 tool-result 错误 + 附"不要立即重新提交"指令。

| 维度 | 方案 1 引导停手 | 你的方案 |
|---|---|---|
| 反馈的模型权重 | 低——tool-result 是"执行失败"语义，模型倾向重试/绕过 | **高**——`role:'user'`，模型倾向遵从 |
| transcript 语义 | 用户的话被塞进错误里，语义失真 | 与用户实际行为一致 |
| 压缩存活 | 反馈细节可能被摘要压掉 | 作为 user 消息进入压缩输入，按用户意图保留 |
| 实现改动 | 零（复用 `AskDeniedError` → tool-result） | 小：`ToolCallResponse` 加字段 + `executeToolsAndBuildParts` 透传 |
| 顺序 / 崩溃安全 | 无风险 | **已不是问题**（见 5.2） |
| 与沙盒提权一致性 | 完全一致（同一出口） | 出口不同——但语义本就不同：提权是**执行许可**，计划审批是**协作决策** |

**结论：采用你的方案。** 方案 1 的唯一优势（零改动）已被现有机制抵消，而它的语义代价是实打实的——这正是 ZCode 在 `turn-control.ts` 注释里写下的理由："feedback 会通过 steer 成为真实 user message"。

### 5.2 实现（v1.1 修订：终止本轮 + 真实用户消息开新轮）

> 初版实现是"隐藏 user 消息注入本轮"（图片注入同款通道）。用户评审指出两条失真：
> 前端不渲染（用户在弹窗里打的话从界面消失）、且逻辑上归属助手轮次。已改为下述语义，
> 初版做法记录于 §附录 偏差 9。

**`followUpUserInput` 的语义一体两面**：工具转交了用户的话 ⇒ 用户开了口 ⇒ **本轮终止**
（`finishReason: "plan_rejected"`），文字随 `run()` 返回值交回 chat-runner，作为
**真实用户消息入队开启新轮次**——与手打消息完全同一条准入路径（`enqueueMessage →
processQueue → startStream → beginTurn → addUserMessage`，scheduler / process_monitor
已有同款先例），因此可见、有独立回合壳、并成为模式切换检测的新基准。

三条路径的产出：

| 情况 | 工具结果 | 轮次 |
|---|---|---|
| 批准 | 计划落盘 + 退出计划态，正常返回 | 当前轮继续，模型开始实施 |
| 拒绝（无文字） | `isError`："The plan was not approved by the user." | **终止**（`plan_rejected`），无新轮次 |
| 自定义回复 | 同上（文案统一） | **终止**；反馈作为真实用户消息**开启新轮次** |

无文字拒绝也终止当前轮（对齐 ZCode："拒绝代表用户要继续讨论，不该当普通工具错误
喂给模型自我重写计划"），且避免模型多回一句"好的，等你指示"。

关键实现点：

1. **引擎**（`agent-engine.service.ts`）：`executeToolsAndBuildParts` 只收集不注入
   （取第一个非空 `followUpUserInput` 随返回值带出）；调用点在 `appendMessages(toolParts)`
   之后发现转交输入即置 `businessReason = "plan_rejected"` 且**不设** `needToContinue`
   ——循环自然退出，`isNormalFinish` 为 false 使 `TURN_STOPPING` 拦截器不会在用户拒绝后
   再注入续跑消息。`run()` 返回值扩展为 `{ finishReason, followUpUserInput? }`。
2. **chat-runner**（`chat-runner.service.ts`）：`finally` 里入队反馈（`QueueSource` 新增
   `"plan_feedback"`，刻意**不进** `toMessageSource` 映射 → 折叠为默认 `kind:'user'`）。
   **必须在 `stopStream` 之后**——此前入队会因 `hasActiveStream=true` 只入队不消费，
   而 `plan_rejected` 不在旧 `NORMAL_FINISH` 门里会无限滞留；`plan_rejected` 已加入该门作兜底。
3. **前端零改动**：新轮次走既有 `turn_start` / `user_message` 事件链路；`finishReason`
   前后端均为自由字符串，未知值静默跳过。

### 5.3 已知取舍

- **崩溃窗口**：反馈文本在"工具结果落库 → run() 返回 → 入队"之间只在内存（毫秒级）。
  `ask/answered` 审计事件已持久化反馈原文，可追溯但不会自动重放。初版的隐藏消息与工具
  结果同批落库、崩溃更安全——这是用崩溃安全性换语义正确性，如实记录。
- **与前端队列的顺序**：若用户此前在手打队列排了消息，`stream_status_changed` 触发的
  前端 drain 可能先开一轮，反馈在后端队列等下一轮——按用户意图时间 FIFO，可接受。

## 6. P3 提示注入（provider + 按周期落库）

### 6.1 插入点与解耦

引擎不再直接调用计划模式工具函数，而是在每个迭代 `getHistory()` 之后向
`TurnReminderRegistry` 收集所有插件注册的提醒：

```ts
const injection = await turnReminders.collect({ sessionContext, iterationCount, history });
if (injection.persist.length) {
  await sessionContext.appendMessages(injection.persist);
  history = await sessionContext.getHistory();
}
const requestMessages = [...history, ...injection.transient];
```

`PlanModePlugin` 在 `onLoad` 时注册 `PlanModeReminderProvider`。引擎只认识
`{ persist, transient }` 通用产物，不 import 任何计划模式代码。

- `persist`：首轮完整提醒 / 退出说明，写入 JSONL，可审计；
- `transient`：同 run 后续迭代的稀疏提醒，只追加到请求尾部，不落库。

两条通道的模型可见文本都统一用 `<system_reminder>...</system_reminder>` 包裹。模型侧 wire 只携带 `role + content`，`kind='model'` / `metadata.hidden` / `source` 都不会发给模型；只有文本标签能让模型识别“这是系统要求，不是用户消息”。

仍然**不改 system prompt**，因此 `getSystemText() + getTools()` 的 KV 前缀保持逐字节稳定。

### 6.2 变体选择

| 条件 | 行为 |
|---|---|
| 当前 epoch 没有可见完整提醒 | `persist` 一条完整工作流（压缩遮蔽后同样成立） |
| 当前 epoch 已有完整提醒 + 首迭代 | 不重复注入（完整版已在历史里） |
| 当前 epoch 已有完整提醒 + 后续迭代 | `transient` 一条稀疏提醒 |
| 已退出且最近标记是 `full` | `persist` 一条退出说明 |
| 已退出且最近标记是 `exit` | 不重复注入 |

完整版约 1.5k tokens，**每个计划周期只落一份**；重进计划模式生成新 epoch。
同 run 后续迭代只给稀疏版，控制 token 成本。

### 6.3 提醒文本（英文，供实现直接使用）

**完整版**：

```

## Plan Workflow

### Phase 1: Initial Understanding
Goal: Gain a comprehensive understanding of the user's request by reading the code and asking questions.

Goal: Design an implementation approach.

- Produce a concrete implementation plan detailed enough to execute.
- Consider the perspectives that matter for this task type:
  - New feature: simplicity vs performance vs maintainability
  - Bug fix: root cause vs workaround vs prevention
  - Refactoring: minimal change vs clean architecture

1. Re-read the critical files to deepen your understanding.
2. Make sure the plan matches the user's original request.
3. If anything is genuinely ambiguous, end your turn with your question.

### Phase 4: Call ExitPlanMode
```

```
Plan mode still active (see the full instructions earlier in the conversation). Read-only. Follow the 4-phase workflow. End your turn with ExitPlanMode when the plan is ready.
```

**退出说明**（持久化，明确覆盖旧指令）：

```
## Exited Plan Mode

You have exited plan mode. The earlier plan-mode instructions (including
"Plan mode is active" and its statement that it supersedes other instructions)
no longer apply. You can now make edits, run commands, and take actions.
```

### 6.4 用户开关的叙事（复用现有机制，零新代码）

扩展既有 `detectModeTransition` **同时检测 `metadata.planEnabled`**，复用现有 `<system_reminder>` + `origin: 'system'` 落库惯例。用户开/关计划模式时模型被告知，**机制现成**。关闭时额外在用户消息 metadata 写 `planModeReminder: 'exit'` + `planModeEpoch`，provider 据此知道最近状态已是 exit，不再重复落退出说明。

### 6.5 模型退出的叙事

`setPlanEnabled(false)` 只落库计划开关，不再维护一次性 flag。下一迭代 provider 扫描历史：`planEnabled === false` 且最近标记是 `full` → `persist` 退出说明。因此进程重启、请求中止都不会丢；用户界面关闭路径由 §6.4 的持久化叙事 + exit 标记覆盖，两条路径不重叠。

## 11. 风险与已知缺口

1. **与 `read-only` 沙盒叠加**：两套机制各拒一次，错误信息可能打架。**门先判**（计划模式是协作状态，先于沙盒强制力）
2. **沙盒二进制缺失**：`run_command` 在计划态直接 fail-closed，计划阶段连只读命令都跑不了。需在 UI 说明，或降级为只读命令白名单（本期不做，先暴露问题）
3. **MCP 工具默认禁止**：依赖 MCP 调研的用户体验下降，需在计划模式提示里说明
4. **提示长度**：完整版约 1.5k tokens/回合，已用"每 run 首迭代"控制
5. **✅ 已补齐（2026-10-15）：模型主动提问工具 `ask_user`**——原缺口是 `AskKind` 里 `'ask'` 已声明但**无任何生产者**，`askService.ask()` 的调用点只有 `ExitPlanMode`（`kind='approval'`），导致计划工作流 Phase 3（澄清需求）只能退化为"结束回合用文本提问"。现由 `backend-ts/src/modules/plugins/builtins/ask-user.plugin.ts` 提供 `ask_user`（一次调用 1–4 题；`questions` schema → `askService.ask(session, { kind: 'ask', questions })`），前端 `SessionCards.vue` **零改动**（分页卡本就渲染 `kind: 'ask'`）。计划提示词同步改写（Phase 1/3/4 + 稀疏提醒）：澄清用 `ask_user`、批准只用 `ExitPlanMode`，两者出口二选一；工具不在册时自动退回"结束回合用文本提问"。

## 附录：落地偏差记录

> 实施过程中与本文档不符之处、以及临时决策。设计意图未变，以下都是实现层面更精确的选择。

### 1. 子会话判定收窄：引入 `requiresUserInteraction`（方案 §3.2 修订）

**原文**：计划门里"子会话一律禁用逃生舱"。
**实际**：新增 `ToolDefinition.requiresUserInteraction`，只对**需要人类应答**的逃生舱工具在子会话失效。

**理由**：原规则会连带禁掉子代理的 `run_command` 只读调研——子代理在计划阶段跑 `git log` 是正当需求。子会话短路的真实目的只是"别让审批卡挂到用户看不见的子会话上卡死父回合"，而这只对阻塞等待人类的工具成立。该字段名与 ZCode 一致，且未来的 `ask_user` 工具（见 §11.5）同样需要它。

### 2. `run_command` 改用逃生舱而非 `readOnly: true`（方案 §3.3 修订）

**原文**："计划模式下 `run_command` 必须声明 `readOnly: true`，否则会被门拒掉"。
**实际**：声明 `allowedInPlanMode: true`，只读性由 handler 在执行期强制（读 `getPlanEnabled()` 决定沙盒档位、拒绝提权参数）。

**理由**：`readOnly: true` 是对工具能力的**永久**声明，而 `run_command` 本质上不是只读工具——那样声明会让该字段在其它消费方（未来可能的 UI 展示、审计）上撒谎。逃生舱的语义"非只读工具但需在计划模式下放行"正好命中。

### 3. 新增 `ToolResultObject.isError`（方案未涉及）

**问题**：工具处理器无法返回**结构化错误**——`isError` 由 `ToolExecutor` 硬编码（成功路径恒 `false`），处理器只能靠 `throw`。但拒绝路径需要同时携带 `followUpUserInput`，而 catch 分支不读该字段。
**实际**：给 `ToolResultObject` 加 `isError?: boolean`，`ToolExecutor` 归一化时透传。这样处理器既能表达"未成功"，又能附带结构化载荷。

### 4. 计划模式持久化落在会话上下文，而非插件（方案 §9 补充）

**问题**：模型经 `ExitPlanMode` 退出必须**自己落库**（否则重启后计划模式复活），但计划模式插件在 `PluginsModule`，而 `PluginsModule → ChatModule` 会成环（`ChatModule → ToolsModule → PluginsModule`）。
**实际**：把持久化放进 `JsonlSessionContext.setPlanEnabled()`，`SessionMetaStore` 经 `JsonlSessionContextFactory` 注入（两者同在 ChatModule，无环）。插件只调 `session.setPlanEnabled(false)`。

**附带发现**：`SessionMetaStore.update` 是**顶层浅合并**（`settings` 整体替换），所以必须读改写——只传 `{ planEnabled }` 会抹掉同一会话的其它设置。已按读改写实现。

### 5. `session/mode_changed` 事件携带 `sandboxMode` 快照（方案 §4.3 扩展）

**实际**：事件数据除 `planEnabled / previousPlanEnabled / source / toolCallId` 外，另带一份 `sandboxMode` 快照（本事件不改变它，仅记录）。

**理由**：为 `安全模式三档方案.md` §6 待办 2（"把 sandboxMode 切换升级为 JSONL log 事件"）预留结构——届时不需改事件形态；同时让审计能还原切换时刻的完整模式全貌。

### 6. 首轮完整提醒按周期落库 + provider 解耦（2026-10-18，取代原“每轮临时”）

**原实现**：`buildPlanModeTurnEntries` 由 agent-engine 直接调用，完整/稀疏提醒全部临时注入、不落库。
**问题**：第二次工具往返后完整指导从请求里消失；稀疏提醒里的“see the full instructions earlier”指向不存在的内容；审计也看不到模型实际收到的完整指导。

**现实现**：
- 新增 `TurnReminderRegistry` / `TurnReminderProvider` 通用 SPI；`PlanModePlugin.onLoad` 注册 provider，引擎只收集 `{ persist, transient }`，不再 import 计划模式代码。
- 完整提醒按 `settings.planModeEpoch` **每周期落库一份**（hidden `kind='model'` 消息，走 `appendMessages`，不能走 `addUserMessage`——后者会写 `kind='user'` 和 `metadata.planEnabled`，污染模式切换基准）。
- 完整/稀疏/退出提醒统一用 `<system_reminder>` 包裹；todo 重注入与已批准计划正文重注入的 `injectUserPrompt` 调用点也同步补标签，保持“系统注入必须可识别”的惯例。
- 压缩遮蔽后 provider 扫描不到完整提醒，会自动补一份；同 run 后续迭代只给稀疏临时提醒。
- 退出检测改为扫描历史最近的 `planModeReminder` 标记，删除 `consumePlanModeExitReminder` 一次性 flag；退出说明也落库，显式覆盖旧指令。
- 用户界面开关补写 `session/mode_changed`（`source='user'`）审计事件；模型退出仍由 `ExitPlanMode` 写 `source='tool'`。
- 标题生成过滤 hidden / `kind='model'` 消息，避免完整提醒污染会话标题。

**代价**：每个计划周期多约 1.5k tokens；压缩后补注入会再产生一份。相比“每回合一份”已是最小增量。

> 参考 `D:\AI\work\public\deepseek-harness` 的 `packages/plan/plan-mode`：它把策略注册为 system prompt section、用 `agent/pre-step` 返回叙事、用 projection 派生状态，引擎无 plan 分支。本实现只借鉴接口分层（provider registry / 历史标记派生退出），**不照搬 system prompt 注入**（会破坏本项目刻意保持的 KV 前缀），也保留 `ToolExecutor` 的硬只读（harness 的计划模式是软约束，不拦工具）。

### 10. 计划历史 v2：单文件覆盖 → toolCallId 身份 + 转录建史 + 每计划一文件（方案 §7 修订，用户评审驱动）

### 11. 新建会话页计划开关修复 + 会话级配置的"两面板接线"（方案 §9 补充）

**问题**：新建会话页由 `CreateSessionChatPanel.vue` 渲染（**不是** `ChatPanel.vue`），P4 只接了后者 → 新建页「计划」按钮点不亮（`chatInputConfig` 无该键、`handleConfigChange` 无该分支、草稿类型无该字段，emit 被静默丢弃）。
**实际**：补齐 5 处接线（草稿类型/初值、`chatInputConfig`、change 类型与分支），值随 `create-session` 载荷提交（后端 `POST /sessions` 本就接受 `settings.planEnabled`）。
**教训**：**会话级配置项必须同时接线两块面板**——`ChatPanel`（既有会话：设置 + 投影 + 防抖保存）与 `CreateSessionChatPanel`（新建草稿：只写草稿、随创建提交），漏一处就是静默失效。

### 12. 新建页默认值记忆：沙盒记住、计划不记（方案未涉及）

### 13. SessionCards 过渡加 `:duration`（实现加固，非方案项）
