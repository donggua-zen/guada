## 0. 结论摘要

**一句话**：会话/消息/智能体/供应商/账户/Bot/MCP/记忆的主体数据能迁移；但**知识库向量 100% 迁移失败**（语义检索静默失效，需自费重嵌入），且**≤ v0.5.2 的老库直跳新版本会整体空转**（会话与消息都不迁移）。这两条建议发版前修掉。

| 等级 | 数据域 | 结论 |
|---|---|---|
| 🔴 P0 | **知识库向量** | 旧向量按 `chunk.id` 匹配，而旧数据的键是 `vector_id` → 实测命中 **0/411**，全部向量丢失 |
| 🔴 P0 | **≤0.5.2 老库直升级** | `_app_migrations` 缺失时把 0002–0005 标记为已执行却不执行 → 会话列表空、消息不迁移（数据未删，可修） |
| 🟠 P1 | 消息重答版本历史 | 每个回合只保留「最新的一条 assistant」，其余版本连同其工具调用/思考永久不迁 |
| 🟠 P1 | 附件元数据 | assistant 产出的文件/图片完全不迁；用户附件只留 4 个字段，`fileId` 等引用丢失 |
| 🟠 P1 | 旧压缩历史 | 每会话只迁 1 条，且一级压缩裁剪前的原文（pruning 原文）永久丢弃 |
| 🟠 P1 | 定时任务 | `characterId` 与 `maxExecutions` 被字段白名单剥离 → 智能体绑定丢失（回退内置 agent）、执行上限失效 |
| 🟠 P1 | 账户密码兜底 | 首次启动若主库瞬时不可读，会写入**无密码**默认账户，之后不再重试导入 |
| 🟡 P2 | 前端偏好 | 3 个 localStorage 键改名/删除且无回退：上次智能体、思考档位、工作区面板常开 |
| 🟡 P2 | 内置主题（打包） | 主题已移入 `plugins/guada-themes`，但打包清单与生产环境变量都不含它 → 非默认主题静默回退 |
| 🟡 P2 | DB 四表 | `user_setting` / `memory` / `character_group` / `session_context_state` 无导出路径（前三张无生产写入，实际无损失） |

## 1. 迁移机制（理解坑的前提）

### 1.1 存储范式变化

旧版权威存储是 Prisma 主库 `ai_chat.db`；新版把主库**冻结为只读迁移源与回滚快照**，权威落到文件域：

| 数据域 | 新权威位置 |
|---|---|
| 会话元数据 | `<sessions根>/_meta.db`（原生 SQLite，版本门 v3） |
| 会话消息 | `<sessions根>/<sessionId>/seg-0000.jsonl`（事件溯源，20MB 分卷） |
| 智能体 | `<dataHome>/agents/<id>/AGENT.md` + `avatar.<ext>` |
| 供应商/模型 | `<dataHome>/providers/<id>.yaml`（模型 id 变为 `{实例id}:{模型名}`） |
| Bot / MCP | `<dataHome>/bots/<id>.yaml`、`<dataHome>/mcp-servers/<id>.yaml` |
| 账户 | `<dataHome>/account.json` |
| 知识库 | `<kb根>/<kbId>/{kb.json,kb.db,raw/<itemId>/}`（`kb.db` 内 `chunk.embedding` + vec0 索引） |
| 记忆 | `<workspace>/.guada/memory/MEMORY.md`（索引）+ 明细文件 |
| 计划 | `<workspace>/.guada/plans/<sessionId>/<planId>.md`（新功能，无老数据） |

Electron 侧数据根目录逻辑与 v0.5.6 一致（`~/.guada` 或老布局 AppData），**根目录不变**，各 store 只是在根下新增子目录。

### 1.2 启动场景判定（`migration-runner.service.ts:78-147`）

| 场景 | 判定条件 | 行为 |
|---|---|---|
| 1 全新安装 | 无业务表 + 无迁移记录 | 执行 baseline（最新全量 schema），标记全部迁移已应用 |
| 2 老库升级 | **有 `session` 表 + 无 `_app_migrations`** | **只写迁移记录，不执行任何迁移**（假设 schema 已就位）⚠ |
| 3 已迁移版本 | 有迁移记录 | 备份后按 id 升序执行 pending 迁移 |

真实库实测印证（本机三份库）：

| 库 | `_app_migrations` | `session.closed_at` | 走向 |
|---|---|---|---|
| `~/.guada/data/ai_chat.db`（v0.5.6 线上态） | 有，仅 `1:baseline` | 无 | 场景 3，0002–0005 正常执行 ✓ |
| `~/.guada-dev/data/ai_chat.db`（已升级） | 5 条全有 | 有 | 迁移链已跑通 ✓ |
| `~/.guada/data - 副本/ai_chat.db`（7 月，≤0.5.2 态） | **无** | 无 | 场景 2，会空转 ⚠ |

### 1.3 编排与失败语义（`migration-bootstrap.service.ts:40-77`）

顺序：DB 结构迁移 → agent → provider → account → metadata(sessions/bots/mcp) → kb → session-messages。
每步 `step()` 捕获异常**只记日志不中断**，各域靠 marker 下次启动重试；门控 30s 超时兜底放行。含义：**迁移失败不会报错给用户，只会表现为「数据暂时不见了」**。

## 2. 逐域审计明细

### 2.1 无缝迁移（主体数据、id 与原值保留）

| 域 | 迁移 | 保真度 |
|---|---|---|
| 会话元数据 | `session`/`session_group` → `_meta.db` | id 原值；`characterId→agentId` 映射；`root_id` 回填；单事务、库内标记，删库即重转 |
| 消息外壳与内容 | `message`/`message_content` → JSONL 事件 | 消息/内容 id 原样保留；`createdAt` 保真；思考文本、工具调用、工具结果、图片块均可表达 |
| 智能体 | `character` → `agents/<id>/AGENT.md` | 头像复制（不删原件）；`.rekey.json` 记录旧 id→目录名 |
| 供应商/模型 | `model_provider`+`model` → `providers/*.yaml` | 已存在文件不覆盖；引用改写 `cuid → {实例id}:{模型名}` |
| 账户 | `user` 表 → `account.json` | `passwordHash` 原样搬运（正常路径） |
| Bot | `bot_instance` → `bots/<id>.yaml` | 丢 `userId`（单账户后无意义）；微信个人号凭据在 `wechat-personal/*.json`，**无需重新扫码** |
| MCP | `mcp_server` → `mcp-servers/<id>.yaml` | 丢 `user_id`（维度取消） |
| 记忆 | `memory/factual.md`+`memos/*.md` → `MEMORY.md` 索引 + `notes/legacy_factual.md` | 懒迁移、复制不删、幂等；仅索引摘要留给 AI 补写 |
| 上传文件 | `file_stores/` 聊天附件目录不动；KB 原件被 **move** 进 `raw/` | KB 原件 move 失败或多引用会留 `failed` 条目（界面可见） |

### 2.2 有损迁移（会丢，且多为静默）

1. **消息重答版本**（`session-message-db-migrator.service.ts:213,232-238`）
   逐个 user 回合只取 `createdAt` 最新的一条 assistant，其余版本及其工具调用/思考/附件不写入 JSONL；`parentId` 非空的孤儿版本整条 `continue` 跳过。被覆盖的旧答案在文件域永久不可见。
2. **附件元数据**（同文件 `:244-251, 275-315, 324-336`）
   - assistant 内容的 `files` **计算了但未使用** → 生成的文件/图片丢失；
   - 用户附件只保留 `{mediaType,bytes,name,url}`，`fileId/contentHash/previewUrl/fileMetadata` 及 `file.content`（DB 内联正文）丢弃；`url` 与 `previewUrl` 均空时附件彻底失联。
3. **旧压缩历史**（同文件 `:538-552`）
   `session_context_state` 每会话只读**一行且无 ORDER BY** → 多次压缩只还原 1 条；一级压缩（pruning）不生成 `message/prune` 事件，`pruning_metadata.prunedContent`（裁剪前原文）与统计**永久丢弃**；用户编辑/删除摘要的能力（API 已删）无等价操作。
4. **定时任务**（`task-storage.service.ts:11-48` + `agent-file-bootstrap.service.ts:296-326`）
   白名单无 `characterId`/`maxExecutions`/`userId`，加载即剥离并落盘；引用改写只处理 `task.agentId`，**v0.5.6 任务用的是 `characterId`**（`git show v0.5.6:.../scheduler.types.ts:21,38,49` 已核实）→ 老任务智能体绑定丢失（运行时回退 `assistant-agent`），`maxExecutions` 上限静默失效（任务可能变无限执行）。
5. **Token 占用锚点近似**：无 provider usage 的回合按「累计字符/4」估算；`compaction/end` 锚点取最后回合值。
6. **回合完成时间**：`turn/finish.time` 用 `updatedAt`（可能被后续编辑/裁剪改写），非真实完成时刻。
7. **迁移中断漏洞**：单会话幂等判据是「JSONL 事件数 >1」，若写盘中途崩溃留下 >1 条完整事件，该会话被判已迁移而跳过，尾部消息静默缺失（需人工 `--force`）。

### 2.3 无法迁移 / 被舍弃

| 对象 | 状态 |
|---|---|
| `session_context_state` 表 | 压缩历史改由 JSONL compaction 事件承载；**裁剪前原文与统计丢弃**（见 2.2-3） |
| `user_setting` / `character_group` / `memory`（DB 表） | 无导出路径、升级即弃（`docs/design/metadata-file-format.md:289-291`）。已核实 v0.5.6 生产代码零访问，实际无损失 |
| `mcp_server.user_id`、`file.upload_user_id` 列值 | 0005 重建表时物理删除（表保留作回滚快照） |
| 旧全局 `vector_db.sqlite` | 改名 `*.pre-sqlite` 保留（不删），但向量匹配失败＝实际丢弃（见 P0-1） |
| 「工作区面板常开」偏好 | `workspaceVisible` 键被显式 `removeItem`，改为会话级默认关闭（`frontend/src/stores/layout.ts:32-51`） |

### 2.4 客户端侧（Electron / 渲染进程）

- **保留**：Electron userData 路径与 `persist:browser_shared` 分区不变 → 登录态、cookie、webview 站点数据、token、语言、主题模式、壁纸、引导完成标记、更新跳过、最近工作区等全部保留；插件目录/清单、技能目录、`plugins_config.json` 格式向后兼容。
- **静默重置**（无旧键回退）：
  - `lastSelectedCharacterId` → `lastSelectedAgentId`（`CreateSessionChatPanel.vue:108,353`）→ 新会话回退到列表首个智能体；
  - `userSelectedThinkingEffort` → `userSelectedThinkingEffort2`（`:114`）→ 思考档位回到模型默认。
- **显式失败**（非静默）：localStorage 里的旧 cuid 模型 id 不迁移，新建会话首次发送报「模型不存在」；`models.json` 中不可解析的引用保持旧值，之后在设置页保存会 400。
- **打包缺口**（✅ 已修复）：10 个内置主题已从 `frontend/public/themes` 移入仓库级插件 `plugins/guada-themes`，但 `package.json` 的 `files`/`extraResources` 都不含 `plugins/`，且生产只设 `PLUGINS_USER_DIR`（不播种）→ 打包版非默认主题静默回退 default（`frontend/src/themes/index.ts:171` 对未知 id 置 pending 不应用）。修复：入口改纯 JS（无依赖 CJS）、新增 `PLUGINS_BUILTIN_DIR` 内置目录扫描（优先于 user/dev）、生产注入 `resources/plugins`、`extraResources` 打入 `plugins/guada-themes`。

## 3. 发版阻断项（P0）

### P0-1 知识库向量全部迁移失败（✅ 已修复）

**根因**：`kb-migration-bootstrap.service.ts` 的 `attachVectors`（修复前）用 `vectors.get(row.id)` 匹配；而

- 旧向量库 `kb_<kbId>` 表的键是 `chunk_<idx>_<fileId>`（`collectVectors` 按其 `id` 建索引）；
- v0.5.6 的 `kb_chunk.id` 是 Prisma cuid，`chunk_<idx>_<fileId>` 存在 **`vector_id` 列**（v0.5.6 `kb-file.service.ts:661`）；
- 采集端其实已经读了 `vectorId`（`:645`），但匹配时未使用。

**实测证据**（本机 v0.5.6 老库 + 老向量库）：

```
kb_chunk: 411 行 ｜ 向量库键: 403 个
按 chunk.id      匹配命中: 0 / 411   ← 当前代码
按 chunk.vector_id 匹配命中: 403 / 411  ← 正确键
```

**后果**：所有旧分块 `embedding = NULL` → `chunk_vec` 索引空 → 语义召回排除缺向量行（`kb-search.service.ts:200`），只剩 FTS 关键词可命中；不报错，只在日志提示跑 `pnpm kb:reembed`（**全量重新嵌入，用户自费，且无 UI 入口**）。

**为什么测试没抓到**：`test/knowledge-base/kb-migration.spec.ts:118-136` 的 fixture 是 `id === vectorId`（`chunk_0_item-1`），恰好绕过了真实形状。

**修复**（一行）：
```ts
const vector = vectors.get(row.vectorId ?? row.id) ?? vectors.get(row.id);
```
并补一条 `id ≠ vectorId`（cuid + `chunk_<idx>_<fileId>`）的回归用例。

**已升级用户的补救**（预备措施）：该缺陷只存在于**未发布的开发提交**（v0.5.6 无 `kb-migration-bootstrap`），出货用户不受影响；若有人跑过中间构建，向量未销毁、仍在 `vector_db.sqlite`（或 `.pre-sqlite` 副本）里，可按 `chunk_${chunk_index}_${item_id}` 组装键回查旧库并 `UPDATE chunk SET embedding=?`，避免全量重嵌入。

**修复落地**：`attachVectors` 改为三层匹配 `vector_id → id → 重建键 chunk_<chunkIndex>_<itemId>`（命中层级进日志）；新增真机形状回归用例（`id` 为 cuid、`vector_id` 为旧键）。

### P0-2 ≤ v0.5.2 老库直跳新版本会整体空转（✅ 已修复）

**根因**：`migration-runner.service.ts:189-205`（场景 2）把全部迁移标记为已应用而不执行。该假设（「schema 已在旧版就位」）对本次发版不成立——0002 要新增 `closed_at/close_reason`，旧库没有这两列，而新 Prisma schema 会全列 SELECT → 读表即 `no such column: closed_at`。

**影响**：会话元数据永不导出（侧栏空）、消息永不迁移成 JSONL、agent/provider 引用改写失败。**数据未删除**，但用户看到「历史全没了」。

**边界**：v0.5.3+ 的老库都有 `_app_migrations`（v0.5.6 线上库实测仅 `1:baseline`），走场景 3 正常迁移——**从 v0.5.6 直升不受影响**；受影响的是跨版本直跳（≤0.5.2 → 新版）。

**修复建议**：场景 2 改为按列/表存在性补执行缺失迁移（0002 幂等化 + 0003/0004/0005 前置 schema 校验），或直接让此类库走 pending 迁移链并给每个迁移加幂等保护（0002 用 `PRAGMA table_info` 判存在）。同时在启动日志中明确打印「检测到旧版库，已执行 N 个结构迁移」。

**修复落地**：场景 2 改为「备份 → 以 baseline 为真源做纯增量 schema 对齐（补表/补列，可空降级并回填占位值）→ 执行全部迁移并记账」，0002 按列存在性幂等化；顺带修复旧库 `file.message_id → content_id` 附件关联回填。真机老库（353 会话/4354 消息/38 附件）实测：行数不变、7 列补齐、外键解除、附件 38 行全部回填。

**可复用校验脚本**（Node + better-sqlite3，在 `backend-ts/` 下运行）：

```js
// 断言旧向量键与分块的对齐率（发版前必须为 100%）
const D = require("better-sqlite3"), os = require("os"), p = require("path");
const vec = new D(p.join(os.homedir(), ".guada/data/vector_db.sqlite"), { readonly: true });
const main = new D(p.join(os.homedir(), ".guada/data/ai_chat.db"), { readonly: true });
const vecIds = new Set();
for (const t of vec.prepare("SELECT name FROM sqlite_master WHERE type='table' AND name LIKE 'kb!_%' ESCAPE '!'").all()) {
  if (t.name.includes("_fts")) continue;
  for (const r of vec.prepare(`SELECT id FROM "${t.name}"`).all()) vecIds.add(String(r.id));
}
const ids = main.prepare("SELECT id, vector_id FROM kb_chunk").all();
const byId = ids.filter((r) => vecIds.has(String(r.id))).length;
const byVec = ids.filter((r) => vecIds.has(String(r.vector_id))).length;
console.log(`chunk=${ids.length} 按id命中=${byId} 按vector_id命中=${byVec}`);
```
