## 项目知识库架构分析（用户要求：后续项目围绕知识库展开）

项目 = GuaDa AI（本地优先 AI 工作站，NestJS + Vue3 + Electron）。

知识库 (RAG) 模块核心事实：

- 位置：`backend-ts/src/modules/knowledge-base/`；底层向量库在 `backend-ts/src/common/vector-db/`（sqlite-vec + FTS5，接口注入 VECTOR_DB，VectorDbService 门面）。
- 数据模型（Prisma/SQLite）：`KnowledgeBase`（绑定 embeddingModelId，chunkMax/Overlap/Min 可配）、`KBFile`（层级目录 parentFolderId 自关联、contentHash、processingStatus/progress 进度、KB 级联删除）、`KBChunk`（vectorId 关联向量库，file 级联删除）。
- 每库一张表 `kb_{kbId}`：主表(向量) + FTS5 虚拟表。jieba(@node-rs/jieba) 中文分词，入库与查询分词逻辑一致。
- 混合检索：双路召回 top_k×4 → 可选 Okapi BM25 重排（IDF 平滑）→ 动态权重（BM25 失效自动降权）→ RRF 融合。REST 默认权重 语义0.3/关键词0.7；Agent 工具 kb_search 默认 0.6/0.4。
- 入库管线（kb-file.service.processFile）：解析(file-parser + ocr) → Token 分块（句子边界优先 + 重叠窗口，NFKC 预处理）→ 清旧数据 → 批量向量化(batch=10, retryWithBackoff, 失败降级逐条) → sqlite-vec + KBChunk 双写 → completed。启动时 resumePendingFileTasks 恢复中断 + cleanupOrphanFiles 清孤儿；换 embedding 模型 → clearAndReprocessKnowledgeBase 全量重建。
- Agent 集成（区别于常规自动 RAG）：不自动注入检索结果；会话消息带 knowledgeBaseIds，Agent 通过插件工具包自主多轮调用：kb_search / kb_list_files / kb_get_chunks / kb_add_document（web 会话才有写入，dangerLevel=high 走审批）。bot 会话 kb 工具包 eager 加载，web 会话 lazy。DocumentPlugin 提供 doc_parse / doc_batch_parse。
- 支持格式：TEXT 类（含 md/txt 等）+ pdf + docx + xlsx（每 Sheet 一页转 Markdown）+ 图片 OCR。
- 前端管理走 REST：knowledge-bases.controller / kb-files.controller / kb-search.controller。

扩展注意点（后续开发约定）：
- 新增入库入口必须复用 KbFileService.processFile，保持进度回调与断点恢复语义。
- 检索走 VectorDbService.searchChunksHybrid，勿绕过门面直接操作 sqlite-vec。
- chunkId 约定 `chunk_{idx}_{fileId}`，vectorId 存回 KBChunk。
- KnowledgeBase embeddingModelId 允许悬空引用（Model 删除不级联），查询前需判空。

## OCR PDF→图片识别方案（进行中）

用户痛点：百度等云 OCR 只收图片不收 PDF，当前 `OcrService.getCapabilities()` 声明 baidu supportsPdf=false，扫描件 PDF 直接跳过 OCR → 文件假完成内容为空。

源码实测关键事实：
- OCR 双 provider：umi（本地，PDF 原生 /api/doc/upload + 图片 /api/ocr）、baidu（云，仅 general_basic 图片，token 自动获取）。
- 扫描件判定 isScanPdf：charCount<50 的页 > 一半 → 整文件判扫描件；混合型 PDF 不触发。
- `recognizeImage` 是死代码（全后端无调用方），图片直传知识库走 detectFileType→unknown→按文本读二进制 = 乱码。文档宣称图片 OCR 未接线。
- 百度 URL L456 读文件输出显示 `access_token=***}` 是脱敏假象，字节级检查确认源码是正常 `${token}` 模板串，非 bug。

方案（已定）：新增 PdfToImageService（pdfjs-dist + @napi-rs/canvas 预编译，流式逐页 AsyncGenerator，默认 scale 2.0，maxPages 200）；能力声明 supportsPdf 布尔 → pdfMode: native|render|none 枚举；recognizePdf 内部分派，render 路径逐页复用 recognizeImage 组装 pages[]；进度映射 15-80% 区间不变；图片守卫最长边 8192px / base64≤4MB / JPEG 降质；失败语义保持抛错。
P0：百度扫描件 PDF 打通（file-parser 零改动）。P1：图片直传接 OCR + 页面级混合检测（charCount<50 的页才 OCR）。P2：umi 失败降级 render、accurate 接口、并发。
风险重点：pdfjs Node 渲染需配 standard_fonts + cmaps 资源；@napi-rs/canvas 要过 Electron rebuild；百度限制以官方文档为准做成常量。

- 新增 `backend-ts/src/common/pdf-render/pdf-to-image.service.ts`：getPageCount + renderPages(AsyncGenerator 流式逐页)；默认 scale 2.0，maxPages 200；最长边≤8192 自动降 scale；体积守卫 PNG→JPEG q85/70/55 阶梯→缩放重渲染一轮→兜底交付；白底填充；cmaps/standard_fonts 用 require.resolve("pdfjs-dist/package.json") 定位。@napi-rs/canvas 是 pdfjs-dist 4.10 的 optionalDependency（随包自带，无需新增依赖），Node 下 DefaultCanvasFactory 自动切换 NodeCanvasFactory，无需传 CanvasFactory。
