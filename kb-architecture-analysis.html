一、核心结论

知识库是 GuaDa AI 的核心 RAG 模块，采用「三层存储 + 双路混合检索 + Agent 自助工具化」三条主线设计：

三层存储：Prisma/SQLite 管元数据与分块正文，sqlite-vec 管向量，FTS5 管倒排索引，原始文件落文件系统——每张知识库对应独立集合 kb_{kbId}，天然实现分区隔离。

混合检索：语义（sqlite-vec）与关键词（FTS5 + jieba 中文分词）双路各召回 top_k×4，可选 Okapi BM25 重排，动态权重降权失效侧，最后 RRF（Reciprocal Rank Fusion）按排名位置融合——不依赖绝对分数，跨引擎可比。

Agent 工具化：与常规"系统自动 RAG 注入"不同，检索策略、轮次、文件组合完全由 Agent 自主决定（kb_search / kb_list_files / kb_get_chunks / kb_add_document 四个工具），写入侧带高危审批。

三、入库管线（processFile）

所有入库入口（前端上传、Agent 的 kb_add_document）最终汇入同一条后台管线，进度实时写库（0-100%），任何一步失败都会落 failed 状态并支持重试：

文件解析（2% → 80%）
按扩展名路由到 TEXT / PDF / DOCX / XLSX 解析器或 OCR，输出带页码的分页文本 parseResult.pages，解析进度映射到全局 2-80%
Token 分块（82% → 86%）
所有页合并为连续文档后统一分块；按 KB 配置 chunkMaxSize=1000 / overlapSize=100；句子边界优先、跨页重叠保留上下文
清理旧数据
重处理场景：先从向量库按 documentId=fileId 删旧向量，再删 KBChunk 记录——保证幂等，失败不阻塞主流程
批量向量化（88% → 93%）
按 KB 绑定的 embeddingModelId 取模型+Provider 配置；批 10 条带重试，失败降级逐条，进度回调逐批写库
双写存储（95% → 100%）
向量 + 元数据写 sqlite-vec（id 约定 chunk_{idx}_{fileId}）；分块正文 + vectorId + token 统计批量写 KBChunk 表；标记 completed
上传/Agent添加 → 保存物理文件(DB: pending) → processFileInBackground → parse(0-80%) → chunk(82-86%) → clean-old → embed(88-93%) → dual-write(95-100%) → completed / failed(可 retry) 启动自愈: onModuleInit → resumePendingFileTasks(恢复中断) + cleanupOrphanFiles(清孤儿) 换模型: update(embeddingModelId变化) → clearAndReprocessKnowledgeBase(清空重建)

四、混合检索机制

searchChunksHybrid 五步流程
步骤机制说明
① 语义召回sqlite-vec 向量相似查询文本先经 embedding 服务向量化，召回 top_k×4 条
② 关键词召回FTS5 + jieba中文用 @node-rs/jieba 精确模式分词，入库与查询分词逻辑一致；bm25() 初排，召回 top_k×4 条
③ BM25 重排（可选）Okapi BM25 公式带 IDF 平滑，在召回集上重算精确分数修正排序；默认开启
④ 动态权重adjustWeights检测 BM25 失效（如查询分词为空）时自动降权关键词侧，防止空结果拖垮融合
⑤ RRF 融合Reciprocal Rank Fusion只依赖双路的排名位置加权融合，不受两套引擎绝对分数量纲差异影响，输出 top_k
分区与过滤

每个知识库独立集合 kb_{kbId}，物理隔离不串库；支持 filter_file_id 把检索范围缩小到单文件（Agent 逐文件深读时用）。

权重默认值

REST API 默认 语义 0.3 / 关键词 0.7（偏关键词精度）；Agent 的 kb_search 默认 0.6 / 0.4（偏语义泛化）——两个入口按场景调了不同先验。

可替换架构

VectorDatabase 是接口（DI 注入 VECTOR_DB token），VectorDbService 是门面；当前实现为 SQLite 系，未来可换 pgvector / Milvus 而不动上层。

六、Agent 集成：与常规 RAG 的本质区别

常规自动 RAG

系统在用户消息后自动检索，把 top-k 片段拼进 prompt——检索时机、轮次、范围全部硬编码，Agent 被动接收结果。

GuaDa 的 Agent 自助模式

会话消息携带 knowledgeBaseIds 绑定范围，Agent 拿到工具后自主决定搜什么、搜几轮、是否深入某文件（search → get_chunks 分页细读）、是否入库新文档。

工具能力约束
kb_search混合检索，返回片段+文件名+chunkIndex需 knowledge_base_id；可 filter_file_id
kb_list_files列文件元数据（状态/进度/chunk 数），分页Agent 可据此判断文件是否处理完成
kb_get_chunks按文件读分块原文，分页（默认 10/页）仅 completed 文件可读
kb_add_document本地文件 → 自动解析/分块/向量化入库dangerLevel=high 走审批；仅 web 会话暴露；bot 会话不开放写入

另有 DocumentPlugin（doc_parse / doc_batch_parse）让 Agent 先解析本地文档再决定入库路径；插件自带使用说明 prompt（搜索优先→分页细读的推荐工作流）。IM（bot）会话中 kb 工具包强制 eager 加载保证可用，web 会话 lazy 按需加载省 token。

七、后续围绕知识库展开的开发约定

入口收敛

新增任何入库入口（API、插件、定时任务、IM 通道）必须复用 KbFileService.processFile 管线，保持进度回调与断点恢复语义，不要自建解析→分块→向量化旁路。

检索走门面

一律经 VectorDbService.searchChunksHybrid / searchChunksSemantic / searchChunksKeyword，不直接操作 sqlite-vec 或 FTS5 表；未来换向量引擎零成本。

ID 与分词约定

向量 id 固定 chunk_{idx}_{fileId} 且同步回 KBChunk.vectorId；FTS5 入库与查询必须共用 jieba 同一分词路径，改分词逻辑需全量重建索引。

悬空引用防护

embeddingModelId 允许悬空（Model 删除不级联），所有取模型配置处必须判空抛错；换模型 = 全量重建，重建期间文件状态重置为 pending。
