三、方案设计

3.1 核心思路：能力声明升级 + 渲染中间层

不改变现有管线结构，做两件事：① PDF→图片渲染服务（新增独立 Service）；② OcrService 能力声明从布尔升级为策略枚举，recognizePdf 内部按策略分派——umi 走原生 PDF 任务（现有逻辑不动），百度等 render 型厂商走"逐页渲染→复用现有图片识别→按页组装"。

recognizePdf(filePath) ├─ pdfMode = "native" → recognizePdfWithUmi (现有逻辑, 不动) ├─ pdfMode = "render" → recognizePdfViaImages (新增) │ → PdfToImageService.renderPages(filePath) 逐页产出 buffer (不落盘) │ → 逐页 recognizeImage(buffer) [umi /api/ocr 或 baidu general_basic] │ → pages[] 组装 → 进度按页占比上报 └─ pdfMode = "none" → 返回 null (现有语义)

3.2 PDF 转图片技术选型

方案 A（推荐）：pdfjs-dist + @napi-rs/canvas

理由：pdfjs-dist 已是项目依赖（文本提取在用），只新增 @napi-rs/canvas 一个预编译原生包（无编译步骤）；与项目现有 native 栈（better-sqlite3 / sqlite-vec / @node-rs/jieba）同构，Windows 桌面端 rebuild-native-modules 与 Docker 镜像均可覆盖；社区有 pdf-to-img 包验证过此组合可行性。

代价：需配置 standardFontDataUrl / cMapUrl 资源（否则部分 PDF 渲染缺字）；Electron 打包需把资源文件带上。

方案 B（备选）：外部二进制（poppler pdftoppm / ImageMagick）

优点：渲染质量最稳，格式兼容性最好。

否决原因：Windows 桌面端要额外分发 exe 并处理 PATH；Docker 镜像要装系统包；部署矩阵（Electron / Web / Docker 三端）维护成本高，与"开箱即用"的产品定位冲突。

折中选项：pdf-to-img npm 包

内部就是 pdfjs-dist + @napi-rs/canvas 的封装，代码量最少；但多一层抽象、需要锁版本防与项目已有 pdfjs-dist 冲突。可作为方案 A 的实现捷径：先直接用该包快速打通，遇到定制需求（只渲染指定页码集合等）再替换为自写渲染层。

3.4 关键设计决策

内存策略：流式逐页

renderPages 用 AsyncGenerator 逐页产出，OCR 完一页释放一页 buffer，只保留文本结果。200 页 PDF 按 scale 2.0 渲染若全量驻留内存可达数 GB，流式是硬要求。

进度映射不变

render 路径的逐页进度上报沿用现有 Umi PDF 的映射区间（15%→80%），file-parser 的 2-80% 全局映射不用改，kb-file 的进度条无感知。

成本护栏

云 OCR 按页计费。maxPages 硬上限 + 处理前日志输出页数与预估调用量；百度免费额度用尽后的计费提醒属于前端设置页职责，不在本期。

失败语义保持

OCR 已配置但识别失败/结果为空 → 抛错（与现状一致），文件状态落 failed 可重试，不做静默降级，避免"假完成"扩散。

五、扫描件判定策略演进（2026-09-01 增补）

原文件级判定 vs 页面级路由（现行为）
维度旧：文件级 isScanPdf新：页面级路由（P1 已实施）
判定粒度charCount<50 的页 > 一半 → 整文件判扫描件，判定即终局每页独立：charCount<50 的页才 OCR，文本页零成本保留，按页码合并
混合 PDF<50% 扫描页时静默丢内容扫描页补 OCR，正文页精确保留
成本整本扫描时全页计费（含有文本层的页）成本 ∝ 真实扫描页数；纯文本 PDF 零调用
水印干扰水印文字抬高 charCount 导致漏判仍用字符阈值（P2 结构信号可解）
为什么不做“全量转图片 OCR”（force-ocr）作为默认

全量 OCR 确实最简单且零漏判，但三个代价：① 云 OCR 按页计费，纯文本 PDF 也白花；② 质量倒退——电子版文本层是精确字符，OCR 会引入错字（0/O、l/1）污染向量索引，直接拉低 RAG 检索质量；③ 延迟。因此保留为可选策略（ocrMode=force），适合本地免费 OCR 或扫描件为主的场景。
